00Git & GitHub — What They Are and How They Work

Version control, branches, remote repositories, pull requests, and the real developer workflow
Git & GitHub
🧒 In simple words

Git is a tool that tracks every change in your project. It lets you save versions, go back in time, and work on different features without breaking the main code. GitHub is a cloud platform where you store your Git repositories online so people can collaborate, review code and deploy projects.

Real-life analogy: Git is like an auto-saving history book for a project. Every time you make a meaningful edit, you create a new checkpoint. GitHub is the shared cloud library where your team stores and shares that book.

Remember: Git = local version control. GitHub = online hosting and collaboration. git commit saves a version locally; git push sends it to GitHub.

What Is Git?

Git is a distributed version control system. That means every developer has a complete copy of the project history on their machine. You can create branches, commit changes, merge them, and restore previous versions without losing work.

01JavaScript — Variables, Data Types & Operators

The absolute foundation — every backend concept builds on this
JS Core
🧒 In simple words

A variable is a labelled box that holds a value. The type says what kind of thing is inside: text (string), a number, true/false (boolean), nothing (null / undefined), or a bigger structure (object / array). Operators are the tools you use on those values: +, ===, &&, ??.

Real-life analogy: Labelled jars in a kitchen. A let jar can be emptied and refilled with something new. A const jar is glued to its label — you can't swap the jar, but if it holds a lunchbox (an object) you can still change what's inside the lunchbox. var is an old jar that leaks outside its shelf (it ignores block scope), which is why nobody uses it any more.

Remember: Use const by default, let only when you reassign, never var. Compare with ===. Primitives are copied by value; objects and arrays are shared by reference.

var / let / const — The 3 Ways to Declare Variables

This is the most important difference to understand before anything else. In modern Node.js (2026) you should only use const and let.

// ── var ── (OLD — avoid completely) ─────────────────────────────────────────
// Function-scoped: ignores if/for blocks
// Hoisted: accessible before declaration (as undefined)
// Can be re-declared: silent bug magnet
function oldWay() {
  console.log(x);  // undefined  (hoisted, NOT error!)
  var x = 5;
  if (true) {
    var x = 10;    // same x! leaks out of the if block
  }
  console.log(x);  // 10  ← changed by the if block. Dangerous.
}

// ── let ── (block-scoped, reassignable) ──────────────────────────────────────
let count = 0;
count = 1;           // ✅ reassign is fine
let count = 2;       // ❌ SyntaxError — cannot re-declare in same scope

if (true) {
  let blockVar = "only here";
}
console.log(blockVar); // ❌ ReferenceError — block scoped

// ── const ── (block-scoped, cannot be reassigned) ────────────────────────────
const MAX_RETRIES = 3;
MAX_RETRIES = 5;       // ❌ TypeError — cannot reassign

// IMPORTANT: const only prevents reassignment, NOT mutation
const user = { name: "Akshat", role: "admin" };
user.role = "user";   // ✅ mutating the object is fine
user = {};              // ❌ reassigning the binding is NOT fine

const arr = [1, 2, 3];
arr.push(4);           // ✅ mutating the array is fine
arr = [1, 2];          // ❌ reassigning is NOT fine

Truthy & Falsy — crucial for backend conditionals

// These 6 values are FALSY — evaluate to false in if()
if (false)      { /* skipped */ }
if (0)         { /* skipped — watch out when checking IDs or counts! */ }
if ("")        { /* skipped */ }
if (null)      { /* skipped */ }
if (undefined){ /* skipped */ }
if (NaN)       { /* skipped */ }

// Everything else is TRUTHY — including these surprises:
if ("0")      { /* runs! — non-empty string */ }
if ([])       { /* runs! — empty array is truthy */ }
if ({})       { /* runs! — empty object is truthy */ }
if (-1)       { /* runs! — any non-zero number */ }

// Real backend usage:

// Optional chaining — safe access on possibly null objects
const city = user?.address?.city ?? "Unknown"; // no crash if address is null
const role = req.user?.role;                    // safe — req.user may be undefined

== vs === — Always use ===

// == (loose) — coerces types before comparing
0 == false         // true  (0 is coerced to false)
"" == false        // true
null == undefined  // true
1 == "1"          // true  (string coerced to number)
[] == false        // true  (bizarre)

// === (strict) — checks both value AND type, no coercion
0 === false        // false ✅
null === undefined // false ✅
1 === "1"         // false ✅

// In backend validation — always === to avoid security holes
if (req.body.role === "admin") { /* exact match */ }
🚫
Using == in authentication or role checks is a security vulnerability. A malicious payload of 0 could match false unexpectedly. Always use ===.

02Deep Copy vs Shallow Copy

One of the most misunderstood concepts — causes subtle, hard-to-find bugs
Memory
🧒 In simple words

When you copy a number or string you get a fully separate copy. When you "copy" an object or array with =, you only copy the address — both names point to the same thing, so changing one changes the other.

Real-life analogy: Sharing a Google Doc link vs downloading a copy. = shares the link — everyone edits the same doc. A shallow copy ({...obj}) is like photocopying the first page: new paper, but the sticky notes attached to it (nested objects) are still the originals. A deep copy (structuredClone) copies every page and every sticky note.

Remember: = → same object. {...obj} / [...arr] → new outer object, shared nested objects. structuredClone(obj) → fully independent. Never mutate req.body or cached objects you didn't create.

The Root Cause — Value vs Reference

This entire topic exists because of how memory works. Primitive values (number, string, boolean) are stored directly in the variable. Objects and arrays store a memory address (reference) pointing to where the actual data lives in the heap.

// PRIMITIVES — copied by VALUE
let a = 42;
let b = a;     // b gets a copy of the VALUE 42
b = 99;
console.log(a); // 42 — a is unaffected. Two separate values in memory.

// OBJECTS — copied by REFERENCE
let obj1 = { name: "Akshat", scores: [10, 20] };
let obj2 = obj1;   // obj2 gets the SAME memory address
                    // obj1 and obj2 point to the SAME object in heap
obj2.name = "Someone";
console.log(obj1.name); // "Someone" !! — obj1 was also changed

// Memory visualised:
// obj1 ──┐
//        ├──→  { name: "Someone", scores: [10,20] }  ← heap
// obj2 ──┘

Shallow Copy — one level deep

A shallow copy creates a new object, but only copies the top-level properties. Nested objects/arrays are still shared by reference — the copy and the original point to the same nested data.

const original = {
  name:   "Akshat",
  role:   "admin",
  scores: [10, 20, 30],        // nested array — reference type
  address: { city: "Delhi" }  // nested object — reference type
};

// ── Methods that do a SHALLOW copy ──────────────────────────────────────────
const copy1 = { ...original };           // spread operator
const copy2 = Object.assign({}, original); // Object.assign
const copy3 = [...original.scores];      // array spread
const copy4 = original.scores.slice();   // array .slice()

// ── What changes — TOP LEVEL (own property) ──────────────────────────────────
copy1.name = "Changed";
console.log(original.name);   // "Akshat" ✅ — top-level string, value copy

// ── What STILL shares — NESTED OBJECTS ──────────────────────────────────────
copy1.scores.push(99);
console.log(original.scores);  // [10, 20, 30, 99] ❌ — SHARED reference!

copy1.address.city = "Mumbai";
console.log(original.address.city);  // "Mumbai" ❌ — SHARED reference!

// Memory visualised:
// original ──→ { name:"Akshat", scores: ──┐, address: ──┐ }
// copy1    ──→ { name:"Changed", scores: ──┘, address: ──┘ }
//                                  ↑ same array!    ↑ same object!
⚠️
Shallow copy is fine when your object only has primitive values at the top level. If it has nested arrays or objects — use deep copy or manually spread the nested parts too.

Deep Copy — fully independent clone

A deep copy creates a completely independent copy at every nesting level. No shared references at all — changing the copy never affects the original.

const original = { name: "Akshat", scores: [10, 20], address: { city: "Delhi" } };

// ── Method 1: structuredClone() ─ modern, built-in, recommended ─────────────
const deep1 = structuredClone(original);
deep1.address.city = "Mumbai";
console.log(original.address.city);  // "Delhi" ✅ — truly independent
// Works with: arrays, nested objects, Date, Map, Set, ArrayBuffer
// Does NOT work with: functions, class instances, undefined

// ── Method 2: JSON round-trip ─ classic, but limited ────────────────────────
const deep2 = JSON.parse(JSON.stringify(original));
// ❌ Loses: functions, undefined, Date becomes string, Map/Set → {}}
// ✅ Works fine for plain JSON-serializable data (most API payloads)

// ── Method 3: lodash cloneDeep ─ handles edge cases ─────────────────────────
const { cloneDeep } = require("lodash");
const deep3 = cloneDeep(original);
// Handles functions, circular references, class instances

// ── Memory visualised ────────────────────────────────────────────────────────
// original ──→ { name:"Akshat", scores:[10,20], address:{city:"Delhi"} }
//                ↑ completely separate objects in heap, no shared refs
// deep1    ──→ { name:"Akshat", scores:[10,20], address:{city:"Mumbai"} }

03Functions — All 7 Types Explained

Declaration, Expression, Arrow, HOF, IIFE, Generator, Async — with backend use cases
Functions
🧒 In simple words

A function is a reusable block of code with a name. You give it inputs (parameters), it does its job, and it can give back a result (return). In JavaScript, functions are also values: you can store them in variables, pass them to other functions and return them.

Real-life analogy: A recipe card. You write the recipe once and cook it many times. Parameters are the ingredients you bring, the return value is the dish. A higher-order function is a recipe that takes another recipe as an ingredient — "take any sauce recipe and pour it over rice". array.map(fn), setTimeout(fn) and app.get(path, fn) all work this way.

Remember: Functions are values. Passing a function to be called later is a callback — the idea that all async code and all Express middleware is built on.

1. Function Declaration

The classic form. Hoisted — can be called before its definition in the file. Good for utility functions and service methods.

// ✅ Works even though call is above definition (hoisted)
greet("Akshat");

function greet(name) {
  return `Hello, ${name}!`;
}

// Default parameters — used heavily in controllers
function buildQuery(page = 1, limit = 10, sort = "createdAt") {
  return { skip: (page - 1) * limit, take: limit, orderBy: { [sort]: "desc" } };
}

// Rest parameters — collect unlimited args into array
function logError(message, ...details) {
  console.error(message, ...details);
}
logError("DB failed", { userId: 1 }, { query: "SELECT..." });

2. Function Expression

A function assigned to a variable. NOT hoisted — must be defined before calling. Useful for conditional function assignment.

// NOT hoisted — ReferenceError if called before this line
const hashPassword = function(password) {
  return bcrypt.hash(password, 12);
};

// Named function expression — name useful for debugging stack traces
const factorial = function fact(n) {
  return n <= 1 ? 1 : n * fact(n - 1);
};

3. Arrow Functions → (most common in modern JS)

Shorter syntax. Critical difference: no own this — inherits this from the outer scope. This makes them perfect for callbacks but problematic inside objects as methods.

// Syntax forms
const add       = (a, b) => a + b;                    // one-line, implicit return
const greet      = name => `Hello ${name}`;             // single param, no parens needed
const getProfile = () => ({ id: 1, name: "Akshat" });  // return object: wrap in ()

// Multi-line arrow — explicit return needed
const createUser = async ({ name, email, password }) => {

4. Higher-Order Functions (HOF)

A function that takes a function as argument OR returns a function. This is the pattern behind Express middleware factories — the most important pattern to understand for backend work.

// ── Takes a function as argument ─────────────────────────────────────────────
// Array methods ARE higher-order functions
users.filter(user => user.active)   // filter takes a callback
users.map(user => user.name)         // map takes a callback

// ── Returns a function — MIDDLEWARE FACTORY PATTERN ──────────────────────────
// This is how Express middleware is made configurable

function authorize(...allowedRoles) {
  // Returns a middleware function — called by Express on each request
  return (req, res, next) => {
    const userRole = req.user?.role;
    if (!allowedRoles.includes(userRole)) {
      return res.status(403).json({ success: false, message: "Forbidden" });
    }
    next();
  };
}

// Usage — authorize("admin") is CALLED, returning the actual middleware
router.delete("/users/:id", authenticate, authorize("admin"), deleteUser);
router.get("/reports", authenticate, authorize("admin", "moderator"), getReports);

// ── validate() — another HOF middleware factory ──────────────────────────────
function validate(schema) {
  return (req, res, next) => {
    const result = schema.safeParse(req.body);
    if (!result.success) {
      return res.status(400).json({ success: false, errors: result.error.flatten() });
    }
    req.body = result.data;  // replace body with cleaned data
    next();
  };
}
router.post("/users", validate(createUserSchema), createUser);

04JS Advanced Concepts for Backend

Closures, classes, error types, prototype — what you actually need
Advanced JS
🧒 In simple words

A closure is a function that remembers the variables from the place where it was created, even after that place has finished running. A class is a template for creating many objects with the same shape and methods.

Real-life analogy: A closure is a backpack. When a function is created, it packs the variables around it into a backpack and carries them wherever it goes. A class is a cookie cutter: one cutter, many cookies (objects), each with its own filling (data) but the same shape (methods).

Remember: Closure = function + remembered variables. It's why authorize("admin") can return a middleware that still knows the role "admin" later. Class = blueprint; new creates an object from it.

Closures — why middleware factories work

A closure is when an inner function remembers variables from its outer scope even after the outer function has returned. This is the mechanism behind every middleware factory.

// Outer function runs once — creates config
function makeRateLimiter(maxRequests, windowMs) {
  const requestCounts = new Map();  // closed over — lives between requests

  // Returns middleware — this is called on EVERY request
  return (req, res, next) => {
    const ip  = req.ip;
    const now = Date.now();
    const userData = requestCounts.get(ip) || { count: 0, start: now };

    if (now - userData.start > windowMs) {
      requestCounts.set(ip, { count: 1, start: now });
      return next();
    }
    if (userData.count >= maxRequests) {
      return res.status(429).json({ message: "Too many requests" });
    }
    userData.count++;
    requestCounts.set(ip, userData);
    next();
  };
}

// maxRequests and windowMs are "closed over" — remembered
app.use("/api", makeRateLimiter(100, 15 * 60 * 1000));

function memoize(fn) {
  const cache = new Map();               // survives between calls thanks to the closure
  return (key) => {
    if (!cache.has(key)) cache.set(key, fn(key));
    return cache.get(key);
  };
}
const slowSquare = (n) => { for (let i = 0; i < 1e8; i++); return n * n; };
const fastSquare = memoize(slowSquare);
fastSquare(9);                           // slow the first time
fastSquare(9);                           // instant — comes from the cache

05OOP — Object-Oriented Programming Concepts

Language-agnostic principles — applicable in JS, Python, Java, any OOP language
OOP
🧒 In simple words

OOP (Object-Oriented Programming) means grouping data and the functions that work on that data together into objects, and hiding the messy details behind a small, clean set of methods.

Real-life analogy: A car. You use the steering wheel, pedals and gear stick (the public methods) without touching the engine (the private data) — that's encapsulation and abstraction. An electric car is still a car (inheritance). Pressing "start" works differently in a petrol car and an electric car, but you press the same button (polymorphism).

Remember: Bundle data + behaviour, keep internals private, expose a small API. In backends you meet OOP in error classes (AppError), services, repositories and models.

What is OOP?

OOP is a programming paradigm (style of thinking about code) where you model your system as a collection of objects — self-contained units that bundle data (attributes) and behaviour (methods) together. The goal is to make code modular, reusable, and easy to reason about.

The 4 core pillars are: Encapsulation, Abstraction, Inheritance, Polymorphism. Every OOP language (JS, Python, Java, C#, Go) implements these — the syntax differs but the concept is identical.

Pillar 1 — Encapsulation

Definition: Bundle data (fields) and behaviour (methods) into one unit (a class), and hide internal details from the outside. The outside world interacts only through a controlled public interface.

Why it matters: Prevents outside code from directly manipulating internal state, which leads to bugs. If you want to change something internal, the public interface stays the same — nothing breaks outside.

// CONCEPT — pseudo-code (not JS-specific)
// BAD — no encapsulation: anyone can set balance to negative
bankAccount.balance = -99999;   // direct mutation — dangerous

// GOOD — encapsulated: balance is private, changed only via methods
class BankAccount {
  constructor(initialBalance) {
    this._balance = initialBalance;   // private — underscore = convention
  }

  deposit(amount) {
    if (amount <= 0) throw new Error("Amount must be positive");
    this._balance += amount;
  }

  withdraw(amount) {
    if (amount > this._balance) throw new Error("Insufficient funds");
    this._balance -= amount;
  }

  getBalance() { return this._balance; }  // read-only access
}

// Outside code CANNOT set balance = -99999 anymore
// It must go through deposit() / withdraw() — which validate first
💡
In backend dev: your UserService class encapsulates all user-related logic. Controllers don't touch the database directly — they call userService.findById(). The service controls how data is accessed.

Pillar 2 — Abstraction

Definition: Hide the complex implementation details and expose only what's necessary. The user of a class/module doesn't need to know how it works — only what it does.

Why it matters: Reduces cognitive load. You can use redis.get("key") without knowing about TCP sockets, serialization, or how Redis stores data in memory.

Pillar 3 — Inheritance

Definition: A class (child) can extend another class (parent), automatically getting all its properties and methods. The child can then add new behaviour or override existing behaviour.

Why it matters: Eliminates duplication. Common logic lives in the parent once; all children get it for free.

// PARENT — general concept
class Error {           // built-in
  constructor(message) {
    this.message = message;
    this.stack   = /* captured */;
  }
}

// CHILD — specialises the parent
class AppError extends Error {
  constructor(message, statusCode) {
    super(message);         // calls parent constructor — gives us this.message
    this.statusCode = statusCode;
    this.isOperational = true;
  }
}

// GRANDCHILD — specialises further
class NotFoundError extends AppError {
  constructor(resource) {
    super(`${resource} not found`, 404);  // hardcodes statusCode = 404
  }
}

// Usage — clean & semantic
throw new NotFoundError("User");
// → { message: "User not found", statusCode: 404, isOperational: true, stack: ... }
⚠️
Composition over Inheritance — a common principle. Deep inheritance chains (A → B → C → D) are hard to understand and refactor. Prefer composing behaviour from smaller pieces. Inheritance is great for 1-2 levels (like AppError extends Error).

Pillar 4 — Polymorphism

Definition: "Many forms." Different objects can be treated as the same type, and each responds to the same method call in its own way. You write code that works with the interface, not the specific implementation.

Why it matters: Makes code extensible. You can add new types without changing existing code.

// CONCEPT — all payment methods share the same interface

class InsufficientFundsError extends Error {
  constructor(balance, amount) {
    super(`Cannot withdraw ₹${amount / 100}; balance is ₹${balance / 100}`);
    this.name = "InsufficientFundsError";
  }

class BankAccount {
  #balance = 0;                   // ENCAPSULATION: private, only this class can touch it
  #history = [];

  constructor(owner) {
    this.owner = owner;
  }

  deposit(paise) {                // ABSTRACTION: callers don't see the rules inside
    this.#assertAmount(paise);
    this.#balance += paise;
    this.#history.push({ type: "CREDIT", paise });
    return this;                  // returning `this` allows chaining
  }

  withdraw(paise) {
    this.#assertAmount(paise);
    if (paise > this.#balance) throw new InsufficientFundsError(this.#balance, paise);
    this.#balance -= paise;
    this.#history.push({ type: "DEBIT", paise });
    return this;
  }

  get balance() { return this.#balance; }           // read-only from outside
  get history() { return [...this.#history]; }      // a copy, so callers can't edit ours

  describe() { return `${this.owner}: ₹${(this.#balance / 100).toFixed(2)}`; }

  #assertAmount(paise) {                            // private helper method
    if (!Number.isInteger(paise) || paise <= 0) throw new RangeError("Amount must be a positive whole number of paise");
  }
}

    this.ratePercent = ratePercent;

    return interest > 0 ? this.deposit(interest) : this;
  }
  describe() {                                      // POLYMORPHISM: same method name, different result
    return `${super.describe()} (savings @ ${this.ratePercent}%)`;
  }
}

06How JavaScript Runs Your Code — Execution Context, Memory & Code Phase

What really happens between "node app.js" and your first console.log
JS Engine
🧒 In simple words

JavaScript does not just start at line 1 and run. It reads your file two times. In the first pass it only makes boxes for every variable and function name (this is the memory phase). In the second pass it runs the code line by line and fills those boxes with real values (this is the code phase).

Real-life analogy: a chef reading a recipe. First they read the whole recipe and place empty bowls with labels on the counter — "flour", "sugar", "eggs". Nothing is cooked yet. Then they cook step by step, filling the bowls and using them. If a step says "make the sauce" (a function call), the chef opens the sauce recipe, does the same two passes for it, finishes it, and comes back to the main recipe exactly where they left off.

Remember: Execution context = the "workspace" where code runs. Memory phase = make the boxes. Code phase = fill the boxes and run. Call stack = the pile of workspaces that are currently open.

The Big Picture — V8 runs the code, libuv does the waiting

This diagram shows everything that happens when Node.js runs the small program in the bottom-left box. Read it in order: the engine creates the Global Execution Context (memory phase, then code phase), functions go onto the call stack, anything slow (a timer, a file read, a network call) is handed to libuv ①, and when it is finished the callback comes back ② through the queues and the event loop.

💡
Small correction you will hear in interviews: timers are not run "inside the thread pool". libuv keeps its own list of timers. The thread pool is used for file system, DNS lookup, crypto and zlib work. Network sockets are watched by the operating system (epoll / kqueue / IOCP). All three are "libuv doing the waiting for you".

What Is an Execution Context?

An execution context is the environment in which a piece of code runs. Think of it as a box that holds three things:

🗂 Memory

All variables and functions of that scope (called the variable environment).

🧵 Code

The "thread of execution" — the line currently being run.

🔗 Outer link

A pointer to the scope it was written inside (for the scope chain) plus the value of this.

There are two kinds you care about:

  • Global Execution Context (GEC) — created once when your file starts. Everything at the top level lives here.
  • Function Execution Context (FEC) — created every time a function is called. Call the same function 1000 times → 1000 separate contexts, one after another. Each one goes through its own memory phase and code phase, and is destroyed when the function returns.

"Hoisting" sounds magical, but it is simply this: names already exist before their line runs, because the memory phase created them. What you get depends on what kind of box was created.

Why This Matters on a Server — A Busy Stack Blocks Everyone

07Async JavaScript — Callbacks, Promises, async/await & Promise.all

How to wait for slow things without freezing the server — and how to run many at once
Async
🧒 In simple words

A backend spends most of its time waiting — for the database, for Redis, for another API. Async code lets JavaScript say "start this, tell me when it's done" and keep doing other work in the meantime.

Real-life analogy: a food court. You order a burger and get a token (that token is a Promise). You don't stand frozen at the counter — you sit, chat, order a drink. When the burger is ready, your token number is called (resolved). If they ran out of buns, they call you to say so (rejected). Promise.all is ordering a burger, fries and a shake at three counters at the same time and eating when all three have arrived.

Remember: A Promise is a token for a future value. await pauses only the current function, never the whole server. Promise.all runs independent tasks in parallel and fails fast if any one fails.

Step 1 — Callbacks (the original way)

A callback is just a function you hand to someone else to call later. Node's older APIs use the error-first callback style: the first argument is an error (or null), the second is the result.

const fs = require("node:fs");

fs.readFile("config.json", "utf8", (err, text) => {
  if (err) return console.error("Could not read file:", err.message);
  console.log("File content:", text);
});
console.log("This prints FIRST — readFile does not wait");

The problem appears when steps depend on each other. Each step needs the previous result, so you nest… and nest… This is callback hell:

getUser(userId, (err, user) => {
  if (err) return handle(err);
  getOrders(user.id, (err, orders) => {
    if (err) return handle(err);
    getPayment(orders[0].id, (err, payment) => {
      if (err) return handle(err);
      sendReceipt(user.email, payment, (err) => {
        if (err) return handle(err);
        console.log("Receipt sent");       // 4 levels deep, error handling repeated 4 times
      });
    });
  });
});

Step 2 — Promises (the token)

A Promise is an object that is always in one of three states:

⏳ pending — still working
→
✅ fulfilled — has a value
or
❌ rejected — has an error

Once a promise is fulfilled or rejected it is settled and never changes again.

// Creating your own promise — wrap something slow
const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

// Wrapping an old callback API
function readJson(path) {
  return new Promise((resolve, reject) => {
    fs.readFile(path, "utf8", (err, text) => {
      if (err) return reject(err);                 // → rejected
      try { resolve(JSON.parse(text)); }           // → fulfilled with the object
      catch (parseErr) { reject(parseErr); }       // bad JSON → rejected
    });
  });
}

// Using a promise with .then / .catch / .finally
readJson("config.json")
  .then((config) => config.port)          // whatever you return goes to the next .then
  .then((port) => console.log("Port is", port))
  .catch((err) => console.error("Failed:", err.message))  // catches errors from ANY step above
  .finally(() => console.log("Done either way"));
💡
Most modern libraries already return promises: fs.promises, mysql2/promise, Prisma, ioredis, fetch. You will rarely write new Promise yourself — mainly to wrap old callback code (or use util.promisify).

Step 3 — async / await (promises that read like normal code)

The same callback-hell example, rewritten. Same behaviour, but flat, readable, and one try/catch handles every step:

async function sendLatestReceipt(userId) {
  try {
    const user    = await getUser(userId);
    const orders  = await getOrders(user.id);
    const payment = await getPayment(orders[0].id);
    await sendReceipt(user.email, payment);
    console.log("Receipt sent");
  } catch (err) {
    handle(err);            // one place for all errors
  }
}

await pauses the function — NOT the server

app.get("/slow", async (req, res) => {
  await sleep(5000);            // this request waits 5 seconds…
  res.send("slow done");
});

app.get("/fast", (req, res) => {
  res.send("fast");             // …but this one still answers instantly in the meantime
});

While /slow is awaiting, its function is parked and the call stack is empty, so the event loop is free to serve /fast. Compare this with the while loop example in the previous section, which really does freeze everyone.

Promise.all — Run Independent Tasks in Parallel

Promise.all([p1, p2, p3]) takes a list of promises and gives back one promise that:

  • Fulfills when all of them fulfill — with an array of results in the same order you passed them (not the order they finished).
  • Rejects as soon as any one rejects — with that first error. This is called fail-fast.

Why it matters — sequential vs parallel

Promise.all — Behaviour You Must Know (with runnable demos)

// helper: resolves (or rejects) with `value` after `ms`
const wait = (ms, value, fail = false) =>
  new Promise((resolve, reject) =>
    setTimeout(() => (fail ? reject(new Error(value)) : resolve(value)), ms));

// 1) Order is preserved — even though "B" finishes first
const r1 = await Promise.all([wait(300, "A"), wait(100, "B"), wait(200, "C")]);
console.log(r1);                 // [ 'A', 'B', 'C' ]  after ~300 ms

// 2) Fail-fast — rejects at 100 ms with the FIRST error
try {
  await Promise.all([wait(300, "A"), wait(100, "B broke", true), wait(200, "C")]);
} catch (err) {
  console.log("Caught:", err.message);   // Caught: B broke
}
// ⚠️ A and C are NOT cancelled — they keep running in the background.
//    If they write to the DB, those writes still happen.

// 3) Plain values are allowed — they are treated as already-resolved
const r3 = await Promise.all([1, "two", wait(50, "three")]);
console.log(r3);                 // [ 1, 'two', 'three' ]

// 4) Empty array resolves immediately
console.log(await Promise.all([]));      // []

How Promise.all works inside (write-it-yourself version)

function promiseAll(items) {
  return new Promise((resolve, reject) => {
    const results = new Array(items.length);
    let finished = 0;
    if (items.length === 0) return resolve([]);

    items.forEach((item, index) => {
      Promise.resolve(item).then((value) => {
        results[index] = value;          // store by INDEX → keeps input order
        finished++;
        if (finished === items.length) resolve(results);
      }, reject);                        // first rejection wins; later ones are ignored
    });
  });
}

Seeing this makes the rules obvious: results are stored by index (order preserved), the first reject call settles the outer promise (fail-fast), and nothing ever stops the other promises (no cancellation).

Promise.all with map — processing a list

// Send a welcome email to every new user — in parallel
const newUsers = await prisma.user.findMany({ where: { welcomed: false } });
await Promise.all(newUsers.map((u) => sendWelcomeEmail(u.email)));

// Upload 3 images to storage in parallel and get their URLs
const urls = await Promise.all(req.files.map((file) => storage.upload(file)));
⚠️
Careful with big lists. Promise.all(10000 items) starts 10,000 operations at the same moment. That can exhaust your DB connection pool (usually 10 connections), hit an email provider's rate limit, or use too much memory. Process in batches instead.
// Run at most `batchSize` operations at a time
async function mapInBatches(items, batchSize, fn) {
  const results = [];
  for (let i = 0; i < items.length; i += batchSize) {
    const batch = items.slice(i, i + batchSize);
    const batchResults = await Promise.all(batch.map(fn));   // parallel inside the batch
    results.push(...batchResults);                           // batches run one after another
  }
  return results;
}

await mapInBatches(newUsers, 20, (u) => sendWelcomeEmail(u.email));   // 20 at a time
🎯
Senior note: batches wait for the slowest item before starting the next batch. A library like p-limit keeps a sliding window (as soon as one finishes, the next starts), which gives better throughput. Also ask whether you need N queries at all — WHERE id IN (…) in one query beats 500 parallel findUnique calls.

Promise.all — The 4 Most Common Mistakes

// ❌ 1. Passing functions instead of calling them
const [a, b] = await Promise.all([getUser, getOrders]);
// a and b are the FUNCTIONS themselves — nothing ran

// ❌ 2. Awaiting inside the array — secretly sequential again
const [user, orders] = await Promise.all([await getUser(id), await getOrders(id)]);
// getOrders only starts after getUser finished → no speed-up

// ❌ 3. Running dependent tasks in parallel
const [u, o] = await Promise.all([getUser(id), getOrders(u.id)]);
// ReferenceError — u does not exist yet. If B needs A's result, await A first.

// ❌ 4. Using Promise.all when partial failure is fine
await Promise.all([sendEmail(), sendSms(), sendPush()]);
// SMS provider down → whole request fails, even though email and push worked
// → use Promise.allSettled (below)

// ✅ Correct
const [user2, orders2] = await Promise.all([getUser(id), getOrders(id)]);

Promise.allSettled — "Tell me how each one went"

Waits for all promises, never rejects, and gives you a report for each one. Use it when one failure should not cancel the others.

const results = await Promise.allSettled([
  sendEmail(user.email, message),
  sendSms(user.phone, message),
  sendPush(user.deviceToken, message),
]);

// results look like:
// [
//   { status: "fulfilled", value: { id: "em_81" } },
//   { status: "rejected",  reason: Error("SMS provider timeout") },
//   { status: "fulfilled", value: { id: "pn_12" } }
// ]

const failed = results.filter((r) => r.status === "rejected");
if (failed.length) {
  logger.warn({ errors: failed.map((f) => f.reason.message) }, "Some notifications failed");
}

Promise.race — first to finish wins

Settles with whichever promise settles first — success or failure. Classic use: a timeout.

function withTimeout(promise, ms, label = "task") {
  let timer;
  const timeout = new Promise((_, reject) => {
    timer = setTimeout(
      () => reject(new Error(`${label} timed out after ${ms}ms`)),
      ms);
  });
  return Promise.race([promise, timeout])
    .finally(() => clearTimeout(timer));
}

const rates = await withTimeout(
  getExchangeRates(), 2000, "rates API");
⚠️
The slow promise is not stopped — it just loses the race. For fetch, really cancel it with fetch(url, { signal: AbortSignal.timeout(2000) }).

Promise.any — first SUCCESS wins

Ignores failures until one succeeds. Rejects only if every promise fails, with an AggregateError.

try {
  const file = await Promise.any([
    download("https://cdn-1.example.com/app.zip"),
    download("https://cdn-2.example.com/app.zip"),
    download("https://cdn-3.example.com/app.zip"),
  ]);
  // fastest working mirror wins
} catch (err) {
  // all 3 failed
  console.log(err.errors.map((e) => e.message));
}

Error Handling — Never Leave a Promise Unhandled

08Node.js System — The Diagram Explained

Every box in the diagram, what it does, and why Node.js doesn't block
Node.js
🧒 In simple words

Node.js = V8 (runs your JavaScript on one thread) + libuv (handles timers, files, network and a small thread pool in the background) + the event loop (decides which finished job's callback runs next).

Real-life analogy: A restaurant with one very fast waiter and a kitchen. The waiter (the JS thread) takes orders and serves plates but never stands at the stove waiting. The kitchen (libuv, the OS and the thread pool) cooks many orders at once. When a dish is ready, a bell rings and the waiter picks it up as soon as their hands are free (the event loop).

Remember: One JavaScript thread, many helpers. Never block the waiter with long CPU work — that's the topic of the next section.

🔗

Every Box Explained — What Each Part Actually Does

📦 Application

Your JavaScript code — Express routes, middleware, controllers, services. This runs entirely in the V8 engine. Only one JS statement executes at a time (single-threaded).

⚙️ V8 Engine

Google's C++ program that compiles your JavaScript to machine code. Manages the call stack (what's currently executing) and the heap (memory for objects). Also runs the garbage collector.

🔗 Node.js Bindings (Node API)

The bridge between your JavaScript and C++ libuv. When you call fs.readFile() in JS, Node bindings translate that call into libuv's C++ API. This is how JS reaches the OS.

🔄 libuv — Asynchronous I/O

A C++ library that gives Node.js its superpowers. It provides an event loop, a thread pool (4 C++ threads by default), and async I/O using the OS's native mechanisms (epoll on Linux, kqueue on macOS).

🔁 Event Loop

The heartbeat of Node.js. Continuously checks: "Is there a completed I/O operation whose callback should run?" It picks up completed callbacks from the event queue and runs them in V8 — one at a time, on the main thread.

🧵 Worker Threads (Thread Pool)

libuv maintains 4 C++ threads (configurable via UV_THREADPOOL_SIZE). Heavy I/O (file reads, DNS lookups, crypto operations) is offloaded here so the main JS thread is never blocked.

The Full Request Flow — step by step

  1. HTTP request arrives
    The OS receives the TCP packet. libuv's network I/O (epoll/kqueue) detects it and places a "new connection" event in the Event Queue.

  2. Event Loop picks it up
    The Event Loop (poll phase) picks the event and invokes your Express route handler in V8 — on the main JS thread.

  3. Route handler calls async I/O
    Your handler calls await prisma.user.findUnique(). This JS call crosses the Node Bindings into libuv. libuv offloads the actual DB socket I/O to the OS (non-blocking).

  4. Main thread is FREE
    While the DB query is in progress (could be 50ms), V8's main thread is not waiting. It goes back to the Event Loop and handles other incoming requests. This is why Node.js serves thousands of concurrent requests with one thread.

  5. I/O completes → callback queued
    The DB returns data. libuv receives it, wraps the callback (your then() or the line after await) and places it in the Event Queue.

  6. Event Loop picks up callback
    On the next iteration, the Event Loop finds your callback, runs it in V8 — your const user = await ... resumes with the result.

  7. Response sent
    res.json(user) runs. libuv writes the HTTP response to the socket. Done.

💡
The key insight: Node.js is NOT blocking during I/O. The single JS thread only runs your actual JS code. All the waiting (network, disk, DB) happens in C++ threads and the OS — completely outside your thread.

09Multithreading & Clustering — Using All Your CPU Cores

Worker threads, the libuv thread pool, child processes, cluster and PM2 — when and how to use each
Scaling
🧒 In simple words

Your JavaScript runs on one thread, which means one CPU core. For waiting-type work (DB, network) that is perfectly fine. But if you have 8 cores, 7 are sitting idle, and one heavy calculation can freeze the whole server.

Real-life analogy: a shop with one cashier.
• Clustering = open 8 identical counters, each with its own cashier. More customers served at once — but each counter has its own cash drawer (memory is not shared).
• Worker threads = the cashier hands a slow job (gift-wrapping 50 boxes) to a helper in the back room, so the queue keeps moving.
• Child process = calling an outside specialist (a tailor) to do a job your staff can't do (run ffmpeg, a Python script).

Remember: Slow because of waiting? Node already handles it. Slow because of CPU work in one route? → worker threads. Need more total throughput? → cluster / PM2 / more containers.

The Problem — One CPU-Heavy Route Freezes Every User

// server.js
const express = require("express");
const app = express();

function fib(n) { return n < 2 ? n : fib(n - 1) + fib(n - 2); }   // deliberately slow

app.get("/health", (req, res) => res.json({ ok: true }));

app.get("/fib/:n", (req, res) => {
  const n = Number(req.params.n);
  res.json({ n, result: fib(n) });     // fib(45) keeps the call stack busy for many seconds
});

app.listen(3000);
# Terminal 1 — start the heavy request
curl localhost:3000/fib/45

# Terminal 2 — immediately try the health check
curl localhost:3000/health     # ⏳ hangs until fib finishes — the event loop is blocked

Remember the rule from the execution section: the event loop can only run a callback when the call stack is empty. While fib(45) runs, the stack is never empty, so /health just waits.

Worker Threads — Run Heavy JavaScript on Another Core

A worker thread is a second JavaScript thread inside the same process. It has its own V8 instance, its own event loop and its own memory. The main thread and the worker talk by sending messages (the data is copied, like posting a letter).

   ┌──────────────── one Node.js process ─────────────────┐
   │                                                       │
   │   Main thread (Express)            Worker thread      │
   │   ┌───────────────────┐  postMessage ┌─────────────┐  │
   │   │ handles requests  │ ───────────→ │ runs fib(45)│  │
   │   │ stays responsive  │ ←─────────── │ on core #2  │  │
   │   └───────────────────┘   result     └─────────────┘  │
   └───────────────────────────────────────────────────────┘
fib.worker.js — the code that runs on the worker thread
const { parentPort, workerData } = require("node:worker_threads");

function fib(n) { return n < 2 ? n : fib(n - 1) + fib(n - 2); }

parentPort.postMessage(fib(workerData.n));    // send the answer back to the main thread
runInWorker.js — wrap the worker in a Promise so you can await it
const { Worker } = require("node:worker_threads");
const path = require("node:path");

function runFibInWorker(n) {
  return new Promise((resolve, reject) => {
    const worker = new Worker(path.join(__dirname, "fib.worker.js"), { workerData: { n } });
    worker.once("message", resolve);                 // the result
    worker.once("error", reject);                    // an exception inside the worker
    worker.once("exit", (code) => {
      if (code !== 0) reject(new Error(`Worker exited with code ${code}`));
    });
  });
}

app.get("/fib/:n", async (req, res) => {
  const result = await runFibInWorker(Number(req.params.n));
  res.json({ result });                              // /health now answers instantly meanwhile
});

Production version — use a worker pool

Starting a new worker costs time and memory (a fresh V8 instance). Creating one per request under load will hurt. A pool starts a few workers once and reuses them. piscina is the standard library for this.

// npm i piscina
const Piscina = require("piscina");
const path = require("node:path");
const os = require("node:os");

const pdfPool = new Piscina({
  filename: path.join(__dirname, "pdf.worker.js"),
  maxThreads: Math.max(1, os.availableParallelism() - 1),   // leave one core for the main thread
});

router.get("/invoices/:id/pdf", authenticate, async (req, res) => {
  const invoice = await invoiceService.getFullInvoice(req.params.id);  // I/O → stays on main thread
  const pdf = await pdfPool.run(invoice);                               // CPU → worker thread
  res.type("application/pdf").send(Buffer.from(pdf));
});
// pdf.worker.js — Piscina calls the exported function with the data you passed
const { renderInvoicePdf } = require("./pdf/render");
module.exports = (invoice) => renderInvoicePdf(invoice);   // returns a Buffer / Uint8Array
🎯
Senior notes: (1) Workers don't share your DB pool, Redis client or Prisma instance — do I/O on the main thread and pass plain data in. (2) Messages are copied with the structured-clone algorithm; for big binary data pass an ArrayBuffer in the transfer list to move it without copying. (3) SharedArrayBuffer + Atomics give real shared memory, but you rarely need it in API servers.

✅ Good jobs for worker threads

  • PDF / Excel / report generation
  • Parsing or transforming a huge CSV / JSON
  • Image processing in pure JS
  • Heavy maths, encryption loops, compression in JS
  • Running an ML model in JS

❌ Don't use them for

  • DB queries, Redis calls, HTTP calls — already non-blocking
  • Small quick tasks — message passing costs more than it saves
  • "Making the whole app faster" — that's clustering

The libuv Thread Pool — Threads You Already Use Without Knowing

libuv has its own pool of 4 C++ threads (by default). Node uses it automatically for: file system calls, dns.lookup, crypto.pbkdf2 / scrypt / randomBytes, zlib compression, and native add-ons like bcrypt. Your JavaScript never runs there — only this built-in C++ work.

// hash.js — 6 expensive hashes at once
const crypto = require("node:crypto");
const start = Date.now();

for (let i = 1; i <= 6; i++) {
  crypto.pbkdf2("secret", "salt", 200000, 64, "sha512", () => {
    console.log(`hash ${i} done after ${Date.now() - start} ms`);
  });
}
# node hash.js  (pool size 4)
hash 1..4 finish at about the same time   ← 4 threads working in parallel
hash 5..6 finish roughly twice as late     ← had to wait for a free thread

# UV_THREADPOOL_SIZE=6 node hash.js   (on a machine with ≥ 6 cores)
all 6 finish at about the same time
⚠️
Real-world symptom: login gets slow under load even though CPU is not at 100% of all cores. Cause: 20 users logging in = 20 bcrypt hashes queued behind 4 pool threads. Fix: raise UV_THREADPOOL_SIZE (set it as an env var before Node starts, up to your core count), rate-limit login, and scale out.

Child Processes — Running Another Program

Use child_process when the work is done by a different program: ffmpeg for video, ImageMagick, a Python ML script, pg_dump/mysqldump for backups.

const { execFile } = require("node:child_process");
const { promisify } = require("node:util");
const execFileAsync = promisify(execFile);

// Make a 640px-wide thumbnail of an uploaded video

// ❌ NEVER build a shell string from user input — command injection:
// exec(`ffmpeg -i ${req.body.file} out.png`)   → file = "x; rm -rf /"
// ✅ execFile with an argument array does not go through a shell

Clustering — One Server Copy per CPU Core

The cluster module starts one primary process that forks several worker processes. Every worker runs your full Express app, and they all share the same port. The primary hands out incoming connections to the workers (round-robin on Linux and macOS).

                    incoming requests on :3000
                              │
                    ┌─────────┴─────────┐
                    │  Primary process  │   (does not run Express —
                    │   pid 4120        │    only manages workers)
                    └─┬──────┬──────┬───┘
                      ↓      ↓      ↓      … one per core
                 Worker 1  Worker 2  Worker 3
                 pid 4127  pid 4128  pid 4129
                 Express   Express   Express
                 own memory own memory own memory   ← nothing shared!
cluster.js
const cluster = require("node:cluster");
const os = require("node:os");

if (cluster.isPrimary) {
  const count = os.availableParallelism();          // number of usable CPU cores
  console.log(`Primary ${process.pid} starting ${count} workers`);
  for (let i = 0; i < count; i++) cluster.fork();

  cluster.on("exit", (worker, code, signal) => {
    console.warn(`Worker ${worker.process.pid} died (${signal || code}) — starting a new one`);
    cluster.fork();                                  // self-healing
  });
} else {
  require("./server");                               // each worker runs the normal app
}
// server.js — add this route to see which worker answered
app.get("/whoami", (req, res) => res.json({ pid: process.pid }));

The #1 Clustering Bug — Memory Is Not Shared

Every worker is a separate process with its own variables. Anything you keep "in memory" silently breaks.

// ❌ Each worker has its OWN copy of this Map
const loginAttempts = new Map();

router.post("/login", async (req, res) => {
  const attempts = (loginAttempts.get(req.ip) ?? 0) + 1;
  loginAttempts.set(req.ip, attempts);
  if (attempts > 5) return res.status(429).json({ message: "Too many attempts" });
  // With 8 workers an attacker gets up to 8 × 5 = 40 tries, spread across workers
});

// ✅ Keep shared state in Redis — every worker (and every server) sees one number
router.post("/login", async (req, res) => {
  const key = `login:attempts:${req.ip}`;
  const attempts = await redis.incr(key);
  if (attempts === 1) await redis.expire(key, 15 * 60);   // 15-minute window
  if (attempts > 5) return res.status(429).json({ message: "Too many attempts" });
  // ...
});

PM2 — Clustering Without Writing cluster.js

In real projects most teams use PM2, a process manager that does clustering, auto-restart, logs and zero-downtime reloads for you.

npm i -g pm2
pm2 start server.js -i max --name api    # cluster mode: one process per core
pm2 list                                 # status, CPU, memory of each process
pm2 logs api                             # live logs from all processes
pm2 reload api                           # zero-downtime: restarts workers one by one
pm2 monit                                # live dashboard
pm2 save && pm2 startup                  # restart everything after a server reboot
// ecosystem.config.js — commit this to the repo
module.exports = {
  apps: [{
    name: "api",
    script: "server.js",
    instances: "max",              // or a number like 4
    exec_mode: "cluster",
    max_memory_restart: "500M",    // restart a worker that leaks memory
    env_production: { NODE_ENV: "production", UV_THREADPOOL_SIZE: 8 },
  }],
};
// pm2 start ecosystem.config.js --env production
💡
In Docker / Kubernetes the usual pattern is the opposite: run one Node process per container and scale by running more containers (replicas: 4). The load balancer spreads traffic and the orchestrator restarts crashed containers. Don't stack PM2 cluster inside every container unless you have a reason — you'd get containers × cores processes.

10HTTP — Requests, Responses, Status Codes & Headers

The language your browser, mobile app and backend speak to each other
HTTP
🧒 In simple words

Every API call is a message from a client to your server, and your server sends a message back. Both messages have the same shape: a first line saying what it is, some headers (labels with extra information), and optionally a body (the actual data).

Real-life analogy: sending a courier parcel. The address is the URL. The instruction "deliver / collect / replace" is the method (GET, POST, PUT…). The labels on the box — "Fragile", "Contains: documents", "Sender ID card attached" — are the headers. What is inside the box is the body. The receipt you get back with "Delivered ✅" or "Address not found ❌" is the status code.

Remember: URL = where. Method = what action. Headers = information about the message. Body = the data. Status code = how it went.

Headers — What They Are

Headers are key: value pairs that carry information about the request or response — who is calling, what format the body is in, how long to cache it, what the client accepts. Three facts to know:

  • Names are case-insensitive. Content-Type, content-type and CONTENT-TYPE are the same. Node stores them in lowercase in req.headers.
  • Values are always strings. Content-Length: 55 arrives as "55".
  • Headers go before the body. Once your server starts sending the body, it can't change the headers any more (source of the famous "headers already sent" error below).

Reading and Setting Headers in Express

router.get("/profile", authenticate, (req, res) => {
  // ── Reading request headers (case-insensitive) ─────────────────────────────
  const auth      = req.get("Authorization");         // "Bearer eyJ…"
  const language  = req.get("accept-language");       // same as req.headers["accept-language"]
  const agent     = req.headers["user-agent"];        // raw object → lowercase keys only!
  const wantsJson = req.accepts("json");              // content negotiation helper

  // ── Setting response headers — BEFORE res.json / res.send ──────────────────
  res.set("Cache-Control", "private, max-age=60");    // browser may cache for 60 s
  res.set({ "Content-Language": "en" });              // several at once
  res.append("Set-Cookie", "theme=dark; Path=/");     // append adds; set replaces
  res.location(`/api/v1/users/${req.user.id}`);       // sets Location

  res.status(200).json({ language, agent });          // sets Content-Type + Content-Length
});

The Error Everyone Hits — "Cannot set headers after they are sent"

Full message: Error [ERR_HTTP_HEADERS_SENT]: Cannot set headers after they are sent to the client. It means your code tried to send two responses to one request.

❌ Missing return — execution continues after the first response

router.get("/users/:id", async (req, res) => {
  const user = await prisma.user.findUnique({ where: { id: Number(req.params.id) } });
  if (!user) {
    res.status(404).json({ message: "User not found" });   // response #1 sent…
  }
  res.json(user);                                          // …response #2 → crash
});

✅ Return (or use else) after sending

if (!user) return res.status(404).json({ message: "User not found" });
res.json(user);

Other common causes: calling next() and res.json() in the same middleware; sending inside a loop; a callback firing twice; setting a header in code that runs after res.json().

11JSON — What It Is and How Express Handles It

From a string of bytes on the network to req.body — and back out with res.json()
JSON
🧒 In simple words

JSON (JavaScript Object Notation) is a way of writing data as plain text so any program — a React app, an Android app, a Python service, your Node server — can read it. A JavaScript object lives in memory; JSON is that object written down as a string so it can travel over the network or be saved in Redis.

Real-life analogy: moving house. Your furniture (the JS object) can't go through the post as it is, so you pack it flat into a box with instructions (JSON.stringify). At the new house someone unpacks and rebuilds it (JSON.parse). Some things don't survive packing — a live plant (a function) or a clock that keeps ticking (a Date becomes just a written time).

Remember: Object → string: JSON.stringify. String → object: JSON.parse. In Express: express.json() does the parse for incoming bodies, res.json() does the stringify for responses.

How Express Turns Raw Bytes into req.body — Step by Step

An HTTP body doesn't arrive as an object. It arrives as a stream of bytes, often split into several chunks. express.json() is a middleware that collects those bytes and parses them.

  1. Check the Content-Type headerIf it isn't application/json, the parser skips the request and req.body stays undefined (Express 5). This is the #1 reason for "req.body is undefined".

  2. Collect chunks, enforce the size limitDefault limit is 100kb. Bigger → error with status 413 (err.type === "entity.too.large"). Protects you from someone sending a 2 GB body.

  3. Decode and parseBytes → UTF-8 text → JSON.parse. Invalid JSON → error with status 400 (err.type === "entity.parse.failed").

  4. Attach and continueThe result is stored in req.body and next() is called, so your route sees a normal object.

What express.json() does — a simplified version you could write yourself

function myJsonParser(req, res, next) {
  if (!req.is("application/json")) return next();      // not JSON → skip

  let raw = "";
  let tooBig = false;
  req.setEncoding("utf8");

  req.on("data", (chunk) => {                          // chunks arrive over time
    raw += chunk;
    if (raw.length > 100_000) tooBig = true;           // real parser counts bytes, not chars
  });

  req.on("end", () => {                                // all chunks received
    if (tooBig) return res.status(413).json({ message: "Body too large" });
    try {
      req.body = raw ? JSON.parse(raw) : {};
      next();
    } catch {
      res.status(400).json({ message: "Invalid JSON in request body" });
    }
  });
}

App structure, routing, request/response, error handling
Express 5
🧒 In simple words

Express is a small library that sits on top of Node's HTTP server and gives you three things: routing (which function handles which URL + method), middleware (functions every request passes through), and helpers on req/res (req.params, res.json()…).

Real-life analogy: a hotel reception. The route table is the list "room service → kitchen, lost key → security, bill → accounts". Middleware is the security check and the register every guest passes first. The handler is the department that actually solves the request.

router.get("/products", async (req, res) => {
  // 1. Read with defaults — every value is a STRING (or missing)
  const {
    category,
    search,
    minPrice,
    maxPrice,
    sort = "-createdAt",
    page = "1",
    limit = "20",
  } = req.query;

  // 2. Convert and clamp — never trust the client
  const pageNum  = Math.max(1, parseInt(page, 10) || 1);
  const limitNum = Math.min(100, Math.max(1, parseInt(limit, 10) || 20));   // cap at 100!

  // 3. Build the filter only from what was provided
  const where = {};
  if (category) where.category = category;
  if (search)   where.name = { contains: search };
  if (minPrice || maxPrice) {
    where.price = {};
    if (minPrice) where.price.gte = Number(minPrice);
    if (maxPrice) where.price.lte = Number(maxPrice);
  }

  // 4. Whitelist sort fields — "-price" means price descending
  const allowedSort = ["price", "createdAt", "name"];
  const field = sort.replace(/^-/, "");
  const orderBy = allowedSort.includes(field)
    ? { [field]: sort.startsWith("-") ? "desc" : "asc" }
    : { createdAt: "desc" };

  const [items, total] = await Promise.all([
    prisma.product.findMany({ where, orderBy, skip: (pageNum - 1) * limitNum, take: limitNum }),
    prisma.product.count({ where }),
  ]);

  res.json({
    success: true,
    data: items,
    meta: { page: pageNum, limit: limitNum, total, totalPages: Math.ceil(total / limitNum) },
  });
});

13Middleware — What It Is, Why It Exists, How to Build It

The core pattern of Express — every request passes through a chain of functions
Middleware
🧒 In simple words

Middleware is a function that runs between the request arriving and your route handler. Each one can read or change req/res, then either pass the request on (next()), finish it (send a response), or report an error (next(err)).

Real-life analogy: Airport security. Check-in counter → baggage scan → passport control → boarding gate. Each station can wave you through, stop you, or send you to a supervisor. You can't skip ahead, and the order of the stations matters.

Remember: Order matters. Every middleware must either respond or call next() — otherwise the request hangs forever. Error-handling middleware has 4 parameters and goes last.

What Is Middleware?

Middleware is a function with access to req, res, and next. It sits between the incoming request and your route handler. Every request travels through middleware functions in the order they are registered.

Think of it like a conveyor belt: the request is the item, middleware functions are the stations, and each station either processes and passes it on (next()) or sends a response (res.json()) to stop the chain.

The 3 Rules of Middleware

// A middleware MUST do exactly ONE of these three things:
// 1. Call next() — pass to next middleware
// 2. Send a response — end the cycle
// 3. Call next(err) — pass to error handler

// ❌ WRONG — does nothing, request hangs forever
app.use((req, res, next) => {
  if (!req.headers.authorization) {
    console.log("no token");  // logs it... but then what?
    // No next(), no response — CLIENT WAITS FOREVER
  }
  next();  // only called if authorized!
});

// ✅ CORRECT — every code path does something
app.use((req, res, next) => {
  if (!req.headers.authorization) {
    return res.status(401).json({ message: "No token" }); // END
  }
  next();  // PASS ON
});
🚫
Use return before res.json() when inside an if-block. Without return, code after the if block runs too, causing "Cannot set headers after they are sent" errors.

function authenticate(req, res, next) {
  const header = req.headers.authorization;
  if (!header?.startsWith("Bearer "))
    return res.status(401).json({ success: false, message: "No token" });

  const token = header.split(" ")[1];
  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET);  // attach user to req
    next();
  } catch (e) {
    if (e.name === "TokenExpiredError")
      return res.status(401).json({ success: false, message: "Token expired", expired: true });
    res.status(403).json({ success: false, message: "Invalid token" });
  }
}

14CORS — Why the Browser Blocks Your API Call and How to Fix It

Origins, preflight requests, credentials, and every common cause of the red console error
CORS
🧒 In simple words

Your React app runs on http://localhost:5173. Your API runs on http://localhost:3000. To the browser these are two different websites. By default, a page from one website is not allowed to read responses from another website. CORS (Cross-Origin Resource Sharing) is how your API tells the browser: "It's OK — I trust that website, let it read my response."

Real-life analogy: an apartment society gate. A delivery person (your frontend's request) arrives at a flat (the API). The security guard (the browser) calls the flat: "Someone from app.shopnow.in is here — allowed?" If the flat says yes (sends the right headers), the guard lets them through. If the flat says nothing, the guard blocks them — even though the flat was reachable. Postman and curl don't have this guard, which is why "it works in Postman but not in the browser".

Remember: CORS is enforced by the browser, fixed on the server (by sending headers). It is not a server error, and it is not a security feature for your API — it protects users of browsers.

The Error You'll See

Access to fetch at 'http://localhost:3000/api/v1/products' from origin 'http://localhost:5173'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the
requested resource.

Read it like a sentence: "The page from localhost:5173 tried to read a response from localhost:3000, and the response did not include permission." Important: in most cases the request did reach your server and your route even ran — the browser only hid the response from your JavaScript.

What Counts as a "Different Origin"?

An origin = scheme + host + port. If any one of the three differs, it's cross-origin.

Page is onCallsSame origin?Why

http://shopnow.inhttps://shopnow.in❌ Crossdifferent scheme

Why browsers do this (the Same-Origin Policy): imagine you're logged into your bank in one tab. You open evil-site.com in another. Its JavaScript calls https://yourbank.com/api/balance — and your browser helpfully attaches your bank cookies. Without the same-origin rule, evil-site could read your balance and statements. CORS is the controlled way to relax that rule only for websites the API owner trusts.

Simple Requests vs Preflight Requests

For "simple" requests the browser sends the request directly and checks the response headers. For anything else it first sends a preflight — an automatic OPTIONS request asking permission.

Simple (no preflight)

  • Method is GET, HEAD or POST
  • Only basic headers (Accept, Content-Language…)
  • Content-Type is only form / text/plain

Preflighted (almost every real API call)

  • Content-Type: application/json
  • An Authorization header
  • Any custom header (X-Request-Id, Idempotency-Key)
  • Methods PUT, PATCH, DELETE

Fixing It in Express — the cors Package

const cors = require("cors");

// ── Development: allow your local frontend ─────────────────────────────────
app.use(cors({ origin: "http://localhost:5173" }));

// ── Production: a whitelist from env + cookies/credentials ─────────────────
// .env → CLIENT_URLS=https://shopnow.in,https://admin.shopnow.in
const allowedOrigins = (process.env.CLIENT_URLS || "").split(",").map((s) => s.trim());

app.use(cors({
  origin(origin, callback) {
    // origin is undefined for curl, Postman, server-to-server and same-origin calls
    if (!origin || allowedOrigins.includes(origin)) return callback(null, true);
    return callback(null, false);   // no CORS headers → the browser blocks the page from reading
  },
  credentials: true,                                   // allow cookies (refresh token)
  methods: ["GET", "POST", "PUT", "PATCH", "DELETE"],
  allowedHeaders: ["Content-Type", "Authorization", "Idempotency-Key", "X-Request-Id"],
  exposedHeaders: ["X-Request-Id", "RateLimit-Remaining"],  // let frontend JS read these
  maxAge: 600,                                         // cache preflight for 10 minutes
}));

// ⚠️ Register cors BEFORE your routes and before authentication middleware,
//    so OPTIONS preflights are answered without needing a token.

What the package does — a hand-written version to understand it

function simpleCors(req, res, next) {
  const origin = req.get("Origin");
  if (origin && allowedOrigins.includes(origin)) {
    res.set("Access-Control-Allow-Origin", origin);   // echo the exact origin back
    res.set("Access-Control-Allow-Credentials", "true");
    res.set("Vary", "Origin");                         // caches must not mix origins
  }
  if (req.method === "OPTIONS") {                      // preflight → answer and stop
    res.set("Access-Control-Allow-Methods", "GET,POST,PUT,PATCH,DELETE");
    res.set("Access-Control-Allow-Headers", "Content-Type,Authorization,Idempotency-Key");
    res.set("Access-Control-Max-Age", "600");
    return res.sendStatus(204);
  }
  next();
}

class AppError extends Error {
  constructor(message, statusCode, errors = null) {
    super(message);
    this.statusCode = statusCode;
    this.status     = statusCode >= 500 ? "error" : "fail";
    this.errors     = errors;
    this.isOperational = true;  // expected error, not a bug
    Error.captureStackTrace(this, this.constructor);
  }
}

const { IS_DEV } = require("../config/env");

module.exports = function errorHandler(err, req, res, next) {
  let statusCode = err.statusCode || 500;
  let message    = err.message || "Something went wrong";

  // ── Handle specific library errors ───────────────────────────────────────

  // Prisma errors
  if (err.code === "P2002") {  // unique constraint failed
    statusCode = 409;
    const field = err.meta?.target?.join(", ");
    message = `${field} already exists`;
  }
  if (err.code === "P2025") {  // record not found
    statusCode = 404;
    message = "Record not found";
  }

  // JWT errors
  if (err.name === "JsonWebTokenError")  { statusCode = 403; message = "Invalid token"; }
  if (err.name === "TokenExpiredError")  { statusCode = 401; message = "Token expired"; }

  // Zod validation
  if (err.name === "ZodError") {
    statusCode = 400;
    message = "Validation failed";
  }

  // Log in development
  if (IS_DEV) console.error("[ERROR]", err);

  // Never leak internal errors in production
  if (statusCode === 500 && !IS_DEV) message = "Something went wrong. Please try again.";

  res.status(statusCode).json({
    success:   false,
    message,
    ...(err.errors   && { errors: err.errors }),
    ...(IS_DEV       && { stack: err.stack }),
  });
};

20Transactions — All or Nothing, Even Under Heavy Traffic

ACID, isolation levels, row locks, optimistic locking, deadlocks — in MySQL, mysql2 and Prisma
Transactions
🧒 In simple words

A transaction is a group of database changes that must all succeed together or all be cancelled together. Either the whole group is saved (COMMIT), or the database acts as if nothing happened (ROLLBACK).

Real-life analogy: sending ₹500 to a friend. Two things must happen: ₹500 leaves your account and ₹500 arrives in theirs. If the server crashes after step one, the money has vanished. A transaction wraps both steps in an "undo-able envelope" — if anything fails, the envelope is torn up and your ₹500 is back as if you never pressed Send.

Remember: Transaction = all-or-nothing for several changes. Lock = "wait your turn" for the same row. You usually need both when money or stock is involved.

ACID — The Four Promises, in Plain Language

LetterMeansBanking example
AtomicityAll steps happen, or none doDebit and credit both happen, or neither
ConsistencyRules (constraints) are never broken after a commitCHECK (balance >= 0), foreign keys, unique keys always hold
IsolationTransactions running at the same time don't see each other's half-finished workYour statement never shows the debit without the matching credit

Transaction Basics in SQL

START TRANSACTION;

UPDATE accounts SET balance = balance - 500 WHERE id = 1;   -- money out
UPDATE accounts SET balance = balance + 500 WHERE id = 2;   -- money in
INSERT INTO transfers (from_id, to_id, amount) VALUES (1, 2, 500);

COMMIT;       -- save all three permanently
-- or
ROLLBACK;     -- undo all three

Autocommit: MySQL runs every statement in its own tiny transaction by default. A single UPDATE is already atomic. You need START TRANSACTION only when several statements must succeed together.

Why Transactions Alone Aren't Enough — The Lost Update

Account balance is ₹1000. Two withdrawal requests arrive at the same moment (maybe a double-click, maybe two devices). Each one does "read balance → check → write new balance".

TimeRequest A — withdraw ₹700Request B — withdraw ₹500Balance in DB
t1SELECT balance → 10001000
t2SELECT balance → 10001000
t31000 ≥ 700 ✔ → UPDATE balance = 300300
t41000 ≥ 500 ✔ → UPDATE balance = 500500 ❌

₹1200 was paid out of a ₹1000 account, and the balance says ₹500. Wrapping each request in a transaction does not fix this — both transactions are individually fine. The problem is that B decided based on a value that was about to change. The fix is locking or an atomic conditional update.

Fix 1 — Pessimistic Locking with SELECT … FOR UPDATE

"Pessimistic" = assume a conflict will happen, so lock first. FOR UPDATE puts an exclusive lock on the rows it reads. Anyone else who wants to lock or change those rows waits until you commit or roll back.

START TRANSACTION;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- lock row 1
-- app checks: balance >= amount ?
UPDATE accounts SET balance = balance - 700 WHERE id = 1;
COMMIT;                                                  -- lock released here
TimeRequest A — ₹700Request B — ₹500Balance
t1SELECT … FOR UPDATE → 1000 🔒1000
t2SELECT … FOR UPDATE → waits…1000
t3UPDATE → 300, COMMIT 🔓still waiting300
t4gets lock, reads 300, 300 < 500 → reject ✔300 ✅
VariantWhat it doesUse for
FOR UPDATEExclusive lock — others can't lock or modifyRead-then-write (balances, stock)
FOR SHAREShared lock — others can read-lock too, but can't modify"Make sure this parent row isn't deleted while I insert a child"
FOR UPDATE NOWAITFail immediately if the row is locked"Seat already being booked" — tell the user instantly
FOR UPDATE SKIP LOCKEDSkip rows other transactions have lockedJob-queue tables: each worker grabs different rows
⚠️
Row locks need an index. InnoDB locks the index records it scans. WHERE id = 1 (primary key) locks one row. WHERE email = ? without an index on email scans — and locks — the whole table, and every other transaction queues behind you.

Fix 2 — Atomic Conditional Update (the simplest, often the best)

For a single row, let the database do check + write in one statement. Row-level locking inside that one UPDATE makes it safe.

const [result] = await pool.execute(
  "UPDATE accounts SET balance = balance - ? WHERE id = ? AND balance >= ?",
  [amount, accountId, amount]
);
if (result.affectedRows === 0) {
  throw new AppError("Insufficient funds", 422);   // the condition failed — nothing changed
}
// Same idea with Prisma
const { count } = await prisma.product.updateMany({
  where: { id: productId, stock: { gte: qty } },
  data:  { stock: { decrement: qty } },
});
if (count === 0) throw new AppError("Out of stock", 409);

Fix 3 — Optimistic Locking with a Version Column

"Optimistic" = assume conflicts are rare, don't lock, but detect them. Each row has a version number. You only update if the version is still what you read.

// 1. Read (no lock)
const [[doc]] = await pool.execute("SELECT id, content, version FROM documents WHERE id = ?", [id]);

// 2. ...user edits for a while...

// 3. Write only if nobody changed it in between
const [r] = await pool.execute(
  "UPDATE documents SET content = ?, version = version + 1 WHERE id = ? AND version = ?",
  [newContent, id, doc.version]
);

  throw new AppError("Someone else edited this document. Reload and try again.", 409);
}

Isolation Levels — How Much Transactions See of Each Other

Isolation is a slider between safety and speed. First, the three "read problems" in simple terms:

  • Dirty read — you read data another transaction hasn't committed yet; it rolls back, and you acted on data that never existed.
  • Non-repeatable read — you read a row twice in one transaction and get two different values because someone committed a change in between.
  • Phantom read — you run the same WHERE query twice and new rows appear, because someone inserted matching rows in between.
LevelDirty readNon-repeatablePhantomNotes
READ UNCOMMITTEDpossiblepossiblepossibleAlmost never used
READ COMMITTED✅ preventedpossiblepossibleDefault in PostgreSQL, SQL Server; fewer locks
REPEATABLE READ✅✅mostly ✅ in InnoDBMySQL InnoDB default. Plain SELECTs read a snapshot; locking reads use gap locks
SERIALIZABLE✅✅✅Safest, slowest — plain SELECTs become locking reads
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;   -- for this connection
SELECT @@transaction_isolation;                           -- check the current level
🎯
Senior note: under REPEATABLE READ, a plain SELECT inside a transaction reads a snapshot taken at your first read — it can show a balance that another transaction has already changed and committed. That's why read-then-write logic must use FOR UPDATE (a locking read sees the latest committed row) or an atomic UPDATE. Raising the isolation level is rarely the right fix.

Deadlocks — Two Transactions Waiting for Each Other Forever

Asha sends money to Ravi (locks Asha's row, then wants Ravi's). At the same moment Ravi sends money to Asha (locks Ravi's row, then wants Asha's). Each holds what the other needs.

   Transfer 1 (Asha → Ravi)          Transfer 2 (Ravi → Asha)
   🔒 lock Asha (id 1)                🔒 lock Ravi (id 2)
   ⏳ wait for Ravi (id 2) ──────┐  ┌── ⏳ wait for Asha (id 1)
                                └──┘
          MySQL detects the cycle → kills one: ER_LOCK_DEADLOCK (1213)

InnoDB notices the cycle within milliseconds and rolls back one transaction (the "victim"). Your code gets an error. Three rules prevent and handle it:

  1. Always lock rows in the same orderSort the ids and lock the smallest first. Both transfers then try to lock id 1 first — one simply waits, no cycle.

  2. Keep transactions shortNo HTTP calls, emails, file uploads or await sleep() inside a transaction. Locks are held until COMMIT.

  3. Retry on deadlockA deadlock victim can safely be retried from the start, a couple of times with a small random delay.

// Lock both accounts in a fixed order — ORDER BY id with FOR UPDATE
const [rows] = await conn.execute(
  "SELECT id, balance FROM accounts WHERE id IN (?, ?) ORDER BY id FOR UPDATE",
  [fromId, toId]
);

// Generic retry helper for deadlocks / lock wait timeouts
async function withRetry(fn, attempts = 3) {
  for (let i = 1; ; i++) {
    try {
      return await fn();
    } catch (err) {
      const retryable = err.code === "ER_LOCK_DEADLOCK" || err.code === "ER_LOCK_WAIT_TIMEOUT";
      if (!retryable || i >= attempts) throw err;
      await new Promise((r) => setTimeout(r, 30 * i + Math.random() * 50));   // back off with jitter
    }
  }
}

To see the last deadlock MySQL detected: SHOW ENGINE INNODB STATUS; → section "LATEST DETECTED DEADLOCK".

Transactions in Node.js — mysql2

The golden rule: every query of a transaction must run on the same connection. pool.query() may pick a different connection each time, so you must take one connection out of the pool.

async function transferMoney(fromId, toId, amount) {
  const conn = await pool.getConnection();            // ← one dedicated connection
  try {
    await conn.beginTransaction();

    const [rows] = await conn.execute(
      "SELECT id, balance FROM accounts WHERE id IN (?, ?) ORDER BY id FOR UPDATE",
      [fromId, toId]
    );
    const sender = rows.find((r) => r.id === fromId);
    if (!sender) throw new AppError("Account not found", 404);
    if (sender.balance < amount) throw new AppError("Insufficient funds", 422);

    await conn.execute("UPDATE accounts SET balance = balance - ? WHERE id = ?", [amount, fromId]);
    await conn.execute("UPDATE accounts SET balance = balance + ? WHERE id = ?", [amount, toId]);
    await conn.execute("INSERT INTO transfers (from_id, to_id, amount) VALUES (?, ?, ?)", [fromId, toId, amount]);

    await conn.commit();                                // all saved
  } catch (err) {
    await conn.rollback();                              // all undone
    throw err;
  } finally {
    conn.release();                                     // ALWAYS give it back to the pool
  }
}

    data:  { stock: { decrement: qty } },

}, {

  maxWait: 2000,        // ms to wait for a connection from the pool
  timeout: 5000,        // ms before Prisma aborts the whole transaction
});

});

Transaction Best Practices — Checklist

  • Short and fast. Only DB work inside. Fetch external data before, send emails / call payment APIs / publish events after commit.
  • Same connection (mysql2) or tx client (Prisma) for every statement.
  • Always rollback in catch and release in finally.
  • Lock in a consistent order and retry deadlocks.
  • Let constraints guard you: UNIQUE, CHECK, FOREIGN KEY — the DB enforces them even when your code has a bug.
  • Index the columns in your locking WHERE so you lock rows, not the table.
  • Don't parallelise inside one transaction — a single connection runs one query at a time anyway; Promise.all inside a transaction just adds confusion.

21Redis — From Zero to Production, the Easy Way

What it is, every data structure with a real use, TTL, caching patterns, cache problems, rate limits, OTPs, queues, atomicity and good practices
Redis
🧒 In simple words

Redis is a super-fast notebook that lives in RAM. You write a value under a name (a key), and later you read it back by that name — usually in well under a millisecond. You can also tell Redis "forget this after 5 minutes", which is why it's perfect for caches, OTPs, sessions and rate limits.

Real-life analogy: MySQL is the office filing cabinet — permanent, organised, can answer complex questions, but you have to walk over and search. Redis is the sticky notes on your monitor — tiny, instant to read, and some of them you throw away at the end of the day. You'd never keep the company's only copy of the accounts on a sticky note, but you'd absolutely stick today's most-asked answers there.

Remember: MySQL = source of truth. Redis = speed layer + shared memory between your servers. If Redis is wiped, your app should become slower, not wrong.

Why Is Redis So Fast? (and Why That Matters to You)

1. Data lives in RAM

Reading RAM takes nanoseconds; even an SSD read plus a SQL query plan takes far longer. A Redis GET on the same network is typically well under 1 ms.

2. Simple structures

No SQL parsing, no joins, no query planner. You ask for exactly one key or one small operation, and Redis does just that.

3. One command at a time

Redis executes commands on a single main thread — the same idea as Node's event loop. No two commands ever run at the same moment.

Point 3 is the one seniors care about: because commands run one after another, every single command is atomic. If 1,000 requests call INCR views at the same instant, Redis lines them up and the final value is exactly 1,000 — no lost updates, no locks needed. The flip side: one slow command blocks everyone, just like a while(true) blocks Node. That's why KEYS * on a big database is banned in production (more on that below).

When to Use Redis — and When Not To

✅ Great fit

  • Caching slow or frequent DB/API results
  • Temporary data with expiry — OTPs, password-reset tokens, email-verify links
  • Counters — views, likes, rate limits
  • Shared state across servers — sessions, refresh tokens, "who is online" (remember cluster mode from Part 2: each process has its own memory)
  • Leaderboards / rankings — sorted sets
  • Background job queues — BullMQ
  • Distributed locks — "only one server runs this cron job" (next sections)

❌ Poor fit

  • The only copy of important data (orders, money, users)
  • Data that doesn't fit in RAM (RAM is expensive)
  • Complex queries — joins, "find all orders over ₹5,000 last month"
  • Data that must be strongly consistent with the DB at every instant
  • "Let's add Redis because it's fast" — without measuring a real slow spot first

A hash is one key holding many small fields. A cart is perfect: key = cart, field = product id, value = quantity.

}

}

TTL (Expiry) — The Feature You'll Use Every Day

TTL = "time to live". A key with a TTL deletes itself when time runs out. This is how you avoid stale cache and memory leaks.

await redis.set("k", "v", "EX", 60);        // expire in 60 seconds
await redis.set("k", "v", "PX", 1500);      // expire in 1500 milliseconds
await redis.set("k", "v", "EXAT", 1790000000); // expire at a Unix timestamp (seconds)
await redis.set("k", "v", "EX", 60, "NX");  // only if key does NOT exist
await redis.set("k", "v2", "XX");           // only if key DOES exist
await redis.set("k", "v3", "KEEPTTL");      // change value, keep the old expiry

await redis.expire("k", 300);               // add/replace a TTL on an existing key
await redis.expire("k", 300, "NX");         // only if it has no TTL yet (Redis 7+)
await redis.ttl("k");                       // seconds left: -1 = no expiry, -2 = key doesn't exist
await redis.persist("k");                   // remove the TTL (key lives forever)

❌ The silent TTL killer

await redis.set("user:42", json, "EX", 300);   // TTL 300
// later, somewhere else, someone updates the value…
await redis.set("user:42", newJson);           // ← TTL is GONE. This key now lives forever.

✅ Always pass EX again (or KEEPTTL)

await redis.set("user:42", newJson, "EX", 300);
// Note: INCR / HSET / LPUSH do NOT touch the TTL — only a plain SET replaces it.

You set a limit with maxmemory (e.g. 512 MB). When it's reached, the maxmemory-policy decides what happens:

Caching Patterns

Cache-Aside (Lazy Loading) — Step by Step

  1. Request asks for product 99

    Look in Redis first: GET product:99.

  2. HIT → return it

    ~1 ms. The database is never touched.

  3. MISS → ask the database

    ~20–200 ms. Then store the answer in Redis with a TTL, so the next request is a hit.

  4. On update/delete → remove the cache key

    The next read misses and loads fresh data.

Instead of copy-pasting this logic in every service, write it once:

src/lib/cache.js — a reusable helper
const redis = require("./redis");

/**
 * cached("product:99", 600, () => db.findProduct(99))
 * - returns cached value if present
 * - otherwise runs loader(), stores the result, returns it
 * - if Redis is down, it quietly falls back to the loader (fail-open)
 */
async function cached(key, ttlSeconds, loader) {
  try {
    const hit = await redis.get(key);
    if (hit !== null) return JSON.parse(hit);           // "null" string → null (cached miss)
  } catch (err) {
    console.warn("cache read failed, using DB:", err.message);
  }

  const value = await loader();

  try {
    // cache "not found" too, but only briefly (stops repeated DB hits for missing ids)
    const base = value == null ? 60 : ttlSeconds;
    const jitter = Math.floor(Math.random() * base * 0.1);   // ±10% so keys don't all expire together
    await redis.set(key, JSON.stringify(value ?? null), "EX", base + jitter);
  } catch (err) {
    console.warn("cache write failed:", err.message);
  }
  return value;
}

async function invalidate(...keys) {
  try { if (keys.length) await redis.unlink(...keys); }      // UNLINK = non-blocking DEL
  catch (err) { console.warn("cache invalidate failed:", err.message); }
}

module.exports = { cached, invalidate };
// product.service.js — using it
const { cached, invalidate } = require("../lib/cache");

function getProduct(id) {
  return cached(`product:${id}`, 600, () =>
    prisma.product.findUnique({
      where: { id },
      select: { id: true, name: true, price: true, stock: true },   // cache only what you need
    })
  );
}

async function updateProduct(id, data) {
  const product = await prisma.product.update({ where: { id }, data });
  await invalidate(`product:${id}`);                                 // AFTER the DB write succeeds
  return product;
}

Invalidating Lists and Search Results

Deleting product:99 is easy. But product 99 also appears in hundreds of cached list pages (products:list:cat=shoes:page=1, …page=2, …sort=price…). Two ways to deal with it:

❌ Deleting with KEYS

const keys = await redis.keys("products:list:*");   // scans EVERY key while blocking Redis
await redis.del(...keys);                          // with 5M keys this freezes Redis for seconds

✅ Option A — version number in the key (no deleting at all)

  const v = (await redis.get("products:ver")) ?? "0";
  return `products:list:v${v}:${new URLSearchParams(filters).toString()}`;

🎓
Senior note — the stale-write race: request A misses the cache and reads the old row; meanwhile request B updates the DB and deletes the key; then A writes the old row into the cache. The cache is now stale until its TTL. That's why every cache key must have a TTL as a safety net, and why very sensitive data (balances, stock for checkout) should be read from the DB, not the cache.

Stampede fix #1 — single-flight inside one process: if 500 requests for the same key arrive in one Node process while the DB call is running, share one promise instead of making 500 DB calls.

const inFlight = new Map();

function singleFlight(key, fn) {
  if (inFlight.has(key)) return inFlight.get(key);          // join the request already running
  const p = fn().finally(() => inFlight.delete(key));
  inFlight.set(key, p);
  return p;
}

// usage: cached() + singleFlight together
const getHomePage = () =>
  singleFlight("home", () => cached("page:home", 60, loadHomePageFromDb));

Stampede fix #2 — across many servers: single-flight only protects one process. With 8 containers, use a short Redis lock so only one of them rebuilds (the full lock pattern is in the Locks section):

async function rebuildOnce(key, ttl, loader) {
  const gotLock = await redis.set(`lock:rebuild:${key}`, "1", "PX", 5000, "NX");
  if (gotLock) {
    try {
      const value = await loader();
      await redis.set(key, JSON.stringify(value), "EX", ttl);
      return value;
    } finally {
      await redis.del(`lock:rebuild:${key}`);
    }
  }
  await new Promise((r) => setTimeout(r, 100));             // someone else is rebuilding — wait a bit
  const hit = await redis.get(key);
  return hit !== null ? JSON.parse(hit) : loader();          // still nothing? fall back to DB
}

Real-World Recipes

Recipe 1 — Rate Limiter (Fixed Window)

"Max 5 login attempts per IP per minute." The counter key lives for 60 s, then resets.

function rateLimit({ prefix, limit, windowSec }) {
  return async (req, res, next) => {
    const key = `rl:${prefix}:${req.ip}`;
    try {
      // MULTI sends both commands together; EXPIRE … NX sets the TTL only on the first hit
      const [[, count]] = await redis.multi().incr(key).expire(key, windowSec, "NX").exec();
      res.set("RateLimit-Limit", String(limit));
      res.set("RateLimit-Remaining", String(Math.max(0, limit - count)));
      if (count > limit) {
        res.set("Retry-After", String(await redis.ttl(key)));
        return res.status(429).json({ success: false, message: "Too many attempts. Try again later." });
      }
    } catch (err) {
      console.warn("rate limiter unavailable:", err.message);   // fail-open: don't block users if Redis is down
    }
    next();
  };
}

app.post("/api/v1/auth/login", rateLimit({ prefix: "login", limit: 5, windowSec: 60 }), login);
💡
Fixed window weakness: 5 requests at 10:00:59 and 5 more at 10:01:00 = 10 in two seconds. If that matters (payments, OTP sending), use a sliding window with a sorted set:
async function slidingWindowAllowed(id, limit, windowMs) {
  const key = `rl:sw:${id}`;
  const now = Date.now();
  const results = await redis.multi()
    .zremrangebyscore(key, 0, now - windowMs)            // drop requests older than the window
    .zadd(key, now, `${now}:${Math.random()}`)           // record this request (unique member)
    .zcard(key)                                          // how many in the window now?
    .pexpire(key, windowMs)                              // tidy up when idle
    .exec();
  return results[2][1] <= limit;
}

const sha256 = (s) => crypto.createHash("sha256").update(s).digest("hex");

async function sendOtp(phone) {
  // 1. cooldown: max one OTP per 60 s. NX means "only if not already set"
  const allowed = await redis.set(`otp:cooldown:${phone}`, "1", "EX", 60, "NX");
  if (!allowed) throw new AppError("Please wait before requesting another OTP", 429);

  const otp = crypto.randomInt(100000, 1000000).toString();   // secure 6-digit code
  await redis.multi()
    .set(`otp:${phone}`, sha256(otp), "EX", 300)              // store a HASH, valid 5 min
    .del(`otp:tries:${phone}`)                                 // reset attempts
    .exec();
  await sms.send(phone, `Your ShopNow code is ${otp}`);
}

async function verifyOtp(phone, input) {
  const tries = await redis.incr(`otp:tries:${phone}`);
  if (tries === 1) await redis.expire(`otp:tries:${phone}`, 300);
  if (tries > 5) throw new AppError("Too many wrong attempts. Request a new OTP.", 429);

  const stored = await redis.get(`otp:${phone}`);
  if (!stored) throw new AppError("OTP expired. Request a new one.", 400);

  const ok = crypto.timingSafeEqual(Buffer.from(stored), Buffer.from(sha256(String(input))));
  if (!ok) throw new AppError("Incorrect OTP", 400);

  await redis.del(`otp:${phone}`, `otp:tries:${phone}`);      // one-time: can't be reused
  return true;
}

Notice how much work TTL does for free: no cron job to clean expired OTPs, no "expires_at" column, no cleanup table.

Doing Several Things Atomically — MULTI, Pipeline, Lua, WATCH

One Redis command is always atomic. But "check stock, then decrement" is two commands, and another client can sneak in between them. Here are your tools:

ToolWhat it guaranteesWhat it does NOT do
PipelineSends many commands in one network trip (speed)Not atomic — other clients' commands can run in between
MULTI / EXECCommands run back-to-back, nobody can interleaveNo rollback; you can't read a value and decide inside it
Lua scriptWhole script runs atomically — you can read, decide and writeMust be short (it blocks Redis while running)
WATCHOptimistic check: EXEC fails if a watched key changedYou must retry; needs its own connection

"No rollback" — see it with your own eyes:

SET name "asha"
MULTI
SET a 1          # QUEUED
INCR name        # QUEUED   ("asha" is not a number — but Redis doesn't check yet)
SET b 2          # QUEUED
EXEC
# 1) OK
# 2) (error) ERR value is not an integer or out of range
# 3) OK          ← a and b were still set! Nothing was undone.

That's the big difference from a SQL transaction. MySQL's ROLLBACK undoes everything; Redis's MULTI just promises "nobody interrupts". This is exactly why money lives in MySQL.

22Redis Locks vs Database Transactions

Distributed locks done right, why the naive version breaks, and exactly when to use a lock, a transaction, or both
Locks
🧒 In simple words

A lock means "only one at a time". A transaction means "all or nothing". They sound similar but solve different problems.

Real-life analogy: a café has one bathroom and one key on a hook. Whoever takes the key goes in; everyone else waits. That's a lock. Now imagine someone takes the key and faints inside — nobody can ever go in again. So the café adds a rule: the key automatically returns to the hook after 10 minutes. That's a lock with a TTL. A transaction is different: it's like a cashier who either completes your whole order (food + payment + receipt) or cancels all of it — never half.

Remember: Transaction = "if anything fails, undo everything" (inside one database). Redis lock = "only one server/process does this right now" (across many servers). A lock never undoes anything.

Why Do We Even Need a Distributed Lock?

In Part 2 you saw that clustering runs your app as several processes, and Docker/Kubernetes run it in several containers. Each one has its own memory, so a JavaScript variable like let isRunning = true only stops that process. Real problems this causes:

SituationWhat goes wrong without a shared lock
Nightly cron "send monthly statements" in 3 containersEvery customer gets 3 emails
Payment gateway sends the same webhook twice, 50 ms apartTwo servers credit the wallet twice
Popular cache key expires8 servers rebuild the same expensive report at once (stampede)
"Generate invoice PDF" clicked twiceTwo PDFs, two invoice numbers

Redis is shared by all servers and executes commands one at a time, so it's the natural place for a "key on the hook".

The One Command Behind Every Redis Lock

SET lock:invoice:42  7f3c9a1e-…  NX  PX 30000
PartMeaningWhy it matters
lock:invoice:42The name of the thing being lockedLock the smallest thing possible — invoice 42, not "all invoices"
7f3c9a1e-…A random token (UUID) unique to this holderProves who owns the lock, so nobody else can release it
NXSet only if the key does not existIf someone already holds it, Redis returns nil → you didn't get the lock
PX 30000Auto-delete after 30,000 msIf your process crashes, the lock frees itself (the fainting-customer rule)

Because it's one command, "check if free" and "take it" happen atomically. Two servers can never both get OK.

Why You Can't Just DEL the Lock When Done

The obvious release is DEL lock:invoice:42. Here's how that deletes someone else's lock:

TimeServer AServer BLock owner in Redis
0 sSET … NX PX 30000 → OKA
0–35 sWork is slow (big PDF, GC pause, slow API)…A
30 s(expired — nobody)
31 sSET … NX → OK, starts workB
35 sFinishes, runs DELnobody ❌ — B's lock deleted
36 sstill working…Server C can now take it too → B and C run together

Fix: release only if the value is still your token. "Check then delete" must be atomic, so it's done in a tiny Lua script:

const RELEASE_LUA = `
  if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
  else
    return 0
  end`;

await redis.eval(RELEASE_LUA, 1, "lock:invoice:42", myToken);   // 1 = number of keys

A Reusable withLock() Helper

src/lib/lock.js
const crypto = require("crypto");
const redis = require("./redis");

const RELEASE_LUA = `
  if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1]) else return 0 end`;
const EXTEND_LUA = `
  if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("PEXPIRE", KEYS[1], ARGV[2]) else return 0 end`;

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function acquire(key, ttlMs) {
  const token = crypto.randomUUID();
  const ok = await redis.set(key, token, "PX", ttlMs, "NX");   // ioredis order: value, "PX", ms, "NX"
  return ok === "OK" ? token : null;
}

/**
 * Runs fn() only if we get the lock.
 * @returns {{ acquired: boolean, result?: any }}
 */
async function withLock(key, fn, { ttlMs = 30_000, retries = 0, retryDelayMs = 200, autoExtend = false } = {}) {
  let token = null;
  for (let attempt = 0; attempt <= retries && !token; attempt++) {
    token = await acquire(key, ttlMs);
    if (!token && attempt < retries) await sleep(retryDelayMs + Math.random() * 100); // jitter
  }
  if (!token) return { acquired: false };

  // "watchdog": keep pushing the expiry forward while fn() is still running
  const timer = autoExtend
    ? setInterval(() => redis.eval(EXTEND_LUA, 1, key, token, ttlMs).catch(() => {}), ttlMs / 3)
    : null;

  try {
    return { acquired: true, result: await fn() };
  } finally {
    if (timer) clearInterval(timer);
    await redis.eval(RELEASE_LUA, 1, key, token).catch(() => {});   // always release, even on error
  }
}

  if (!first) return console.log("Another instance already ran today's statements");

  await sendDailyStatements();   // make this idempotent too (see below) in case it crashes half-way
});

The Hard Truth — TTL vs "My Work Took Longer"

Every Redis lock has a gap: if your process freezes longer than the TTL (long GC pause, laptop sleep, network hiccup), the lock expires while you still think you hold it. Three ways to live with that:

  1. TTL comfortably longer than the work

    Measure the job's p99 duration; set TTL to several times that.

  2. Auto-extend (watchdog)

    The autoExtend option above renews the lock every TTL/3 while the work is running. If the process dies, renewals stop and the lock expires.

  3. Fencing tokens — the only truly safe option

    Each time the lock is taken, also take an increasing number (INCR fence:payouts → 33, 34, 35…). The database only accepts writes with a number higher than the last one it saw, so a "zombie" holder with token 33 is rejected after holder 34 has written.

const fence = await redis.incr("fence:payout:77");      // e.g. 34
// ... slow work ...
const [r] = await db.query(
  "UPDATE payouts SET status = 'SENT', fence = ? WHERE id = ? AND fence < ?",
  [fence, 77, fence]
);
if (r.affectedRows === 0) throw new Error("Stale lock holder — a newer holder already wrote");
🎓
Senior note — efficiency vs correctness. Use a Redis lock for efficiency: "avoid doing the same work twice; if it rarely happens twice, nothing breaks". For correctness — "money must never move twice" — the final guarantee must come from the database: transactions, row locks, unique constraints, fencing. Redlock (locking on a majority of several independent Redis servers) survives one Redis crashing, but it still depends on timing, so the same rule applies.

Using Both Together — A Payment Webhook

The gateway may send the same event twice, even at the same moment to two different servers. Layers of protection:

router.post("/webhooks/payments", express.raw({ type: "application/json" }), async (req, res) => {
  verifySignature(req);                                   // reject fakes first
  const event = JSON.parse(req.body);

  // Layer 1 (efficiency): only one server processes this event at a time
  const { acquired } = await withLock(`lock:webhook:${event.id}`, async () => {
    try {
      // Layer 2 (correctness): unique index on provider_event_id + one transaction
      await prisma.$transaction(async (tx) => {
        await tx.processedEvent.create({ data: { providerEventId: event.id } }); // duplicate → P2002
        await applyPayment(tx, event);                    // credit wallet, write ledger rows
      });
    } catch (err) {
      if (err.code !== "P2002") throw err;                // P2002 = already processed → fine, do nothing
    }
  });

  // Not acquired? Another server is on it. A non-2xx makes the gateway retry later,
  // and by then the event is recorded, so the retry becomes a harmless no-op.
  if (!acquired) return res.sendStatus(409);
  res.sendStatus(200);
});

Even if Redis were down or the lock expired early, the unique index would still stop the double credit. The lock is a performance helper; the database is the safety net.

23Authentication & JWT — Deep Dive

How JWT works internally, register/login flow, refresh tokens, RBAC
Auth
🧒 In simple words

Authentication = proving who you are (login). Authorization = what you're allowed to do (roles, ownership). A JWT is a signed token the server gives you after login, which you send back with every request.

Real-life analogy: A festival wristband. You show your ID at the gate once (login) and get a wristband (JWT). Staff anywhere in the festival can check it just by looking at the hologram (the signature) — no need to call the gate. Anyone can read what's printed on it, but nobody can make a fake one without the hologram stamp (the secret key).

Remember: A JWT is signed, not encrypted — never put passwords or private data in it. Keep access tokens short-lived and verify them on every request.

What is JWT? — How it works internally

JWT (JSON Web Token) is a self-contained token — it carries the user's information inside itself, so the server doesn't need to look anything up in a database on every request.

// A JWT has 3 parts separated by dots:
// eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9  ← HEADER (base64)
// eyJ1c2VySWQiOjEsInJvbGUiOiJ1c2VyIn0   ← PAYLOAD (base64)
// SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c  ← SIGNATURE (HMAC-SHA256)

// ── Header — algorithm info ──────────────────────────────────────────────────
{ "alg": "HS256", "typ": "JWT" }

// ── Payload — user data (NOT encrypted, just encoded!) ──────────────────────
{
  "userId": 1,
  "role": "admin",
  "iat": 1700000000,  // issued at (UNIX timestamp)
  "exp": 1700000900   // expiry (15 minutes later)
}

// ── Signature — prevents tampering ──────────────────────────────────────────
// HMAC-SHA256(base64(header) + "." + base64(payload), JWT_SECRET)
// If anyone changes the payload, the signature won't match → rejected
⚠️
The payload is BASE64 encoded, not encrypted. Anyone can decode it (no password needed). Never put sensitive data (password, card numbers) in a JWT payload. Only put what you need for authorization (userId, role).

Complete Auth Service — Register & Login

// services/auth.service.js
const bcrypt = require("bcryptjs");
const jwt    = require("jsonwebtoken");

const register = async ({ name, email, password }) => {
  // 1. Check email not taken
  const exists = await prisma.user.findUnique({ where: { email } });
  if (exists) throw new AppError("Email already registered", 409);

  // 2. Hash password — NEVER store plain text
  const hashed = await bcrypt.hash(password, 12);  // 12 = saltRounds

  // 3. Create user — only return safe fields
  const user = await prisma.user.create({
    data: { name, email, password: hashed },
    select: { id: true, name: true, email: true, role: true }
  });

  // 4. Generate tokens
  const tokens = generateTokens(user);

  // 5. Queue welcome email (non-blocking)
  emailQueue.add("welcome", { email, name });

  return { user, ...tokens };
};

const login = async ({ email, password }) => {
  // 1. Find user — include password for comparison
  const user = await prisma.user.findUnique({ where: { email } });

  // 2. Vague error — don't reveal whether email exists
  if (!user || !(await bcrypt.compare(password, user.password))) {
    throw new AppError("Invalid email or password", 401);
  }

  // 3. Generate tokens
  const { password: _, ...safeUser } = user;
  return { user: safeUser, ...generateTokens(user) };
};

// ── Token generation ─────────────────────────────────────────────────────────
function generateTokens(user) {
  const accessToken = jwt.sign(
    { userId: user.id, role: user.role },
    process.env.JWT_SECRET,
    { expiresIn: "15m" }   // short-lived — if stolen, expires soon
  );
  const refreshToken = jwt.sign(
    { userId: user.id },
    process.env.JWT_REFRESH_SECRET,
    { expiresIn: "7d" }    // long-lived — stored securely
  );

  // Store refresh token in Redis to allow revocation
  redis.set(`refresh:${user.id}`, refreshToken, "EX", 7 * 24 * 60 * 60);

  return { accessToken, refreshToken };
}

// ── Token refresh ────────────────────────────────────────────────────────────
const refreshAccessToken = async (refreshToken) => {
  const decoded = jwt.verify(refreshToken, process.env.JWT_REFRESH_SECRET);

  // Verify token hasn't been revoked (e.g., user logged out)
  const stored = await redis.get(`refresh:${decoded.userId}`);
  if (stored !== refreshToken) throw new AppError("Refresh token revoked", 403);

  const user = await prisma.user.findUnique({ where: { id: decoded.userId } });
  return { accessToken: jwt.sign({ userId: user.id, role: user.role }, process.env.JWT_SECRET, { expiresIn: "15m" }) };
};

// ── Logout ───────────────────────────────────────────────────────────────────
const logout = async (userId) => {
  await redis.del(`refresh:${userId}`);  // revoke the refresh token
};

Look Inside a Token With Your Own Eyes

A JWT is three Base64URL pieces joined by dots: header.payload.signature. Anyone holding it can read the first two — no secret needed:

const jwt = require("jsonwebtoken");

const token = jwt.sign({ sub: "42", role: "user" }, process.env.JWT_SECRET, { expiresIn: "15m" });
const [header, payload, signature] = token.split(".");

JSON.parse(Buffer.from(header, "base64url").toString());    // { alg: 'HS256', typ: 'JWT' }
JSON.parse(Buffer.from(payload, "base64url").toString());   // { sub: '42', role: 'user', iat: …, exp: … }

But try to change it — for example promote yourself to admin — and the signature no longer matches:

const fakePayload = Buffer.from(JSON.stringify({ sub: "42", role: "admin" })).toString("base64url");
const forged = `${header}.${fakePayload}.${signature}`;

jwt.verify(forged, process.env.JWT_SECRET, { algorithms: ["HS256"] });
// ❌ throws JsonWebTokenError: invalid signature

❌ Putting private data in the payload

jwt.sign({ id: user.id, email: user.email, password: user.password, pan: user.pan }, secret);
// anyone who sees the token (browser storage, logs, proxies) can read all of this

✅ Only an id and what's needed for authorization

jwt.sign({ sub: String(user.id), role: user.role }, secret, { expiresIn: "15m" });
// verify with a fixed algorithm list so a token can't pick its own algorithm
jwt.verify(token, secret, { algorithms: ["HS256"] });

24Session vs JWT — When to Use What

Two completely different approaches to auth — with real tradeoffs
Session & JWT
🧒 In simple words

After login the server has to remember you. A session keeps your login data on the server and gives your browser only an ID in a cookie. A JWT puts the login data inside the token itself.

Real-life analogy: A coat check. With a session you get a numbered ticket; your coat (data) stays at the counter (server / Redis), and the counter can refuse your ticket any time. With a JWT you carry everything on a wristband yourself — no counter needed, but the wristband stays valid until it expires.

Remember: Sessions are easy to revoke but need shared storage (Redis) when you run many servers. JWTs need no storage but are hard to revoke — so use short-lived access tokens plus refresh tokens.

How Each Works

Sessions (Stateful)

// On login:
// 1. Server creates session record in DB/Redis
// 2. Returns a session ID cookie to client
// On each request:
// 1. Client sends session ID cookie
// 2. Server looks up session in Redis
// 3. Gets full user data
// 4. Processes request

const session = require("express-session");
const RedisStore = require("connect-redis").default;

app.use(session({
  store: new RedisStore({ client: redis }),
  secret: process.env.SESSION_SECRET,
  resave: false,
  saveUninitialized: false,
  cookie: {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    maxAge: 24 * 60 * 60 * 1000  // 1 day
  }
}));

// Login — save to session
req.session.userId = user.id;

// In middleware — lookup session
const userId = req.session.userId;
if (!userId) return res.status(401).send();

// Logout — destroy session
req.session.destroy();

JWT (Stateless)

// On login:
// 1. Server signs a token with user data inside
// 2. Returns token to client
// On each request:
// 1. Client sends token in Authorization header
// 2. Server verifies signature (math, no DB lookup)
// 3. Decodes user data from token
// 4. Processes request

// Login — sign token
const token = jwt.sign(
  { userId: user.id, role: user.role },
  process.env.JWT_SECRET,
  { expiresIn: "15m" }
);
res.json({ token });  // or set as httpOnly cookie

// In middleware — verify token (NO DB call)
const token = req.headers.authorization?.split(" ")[1];
const decoded = jwt.verify(token, process.env.JWT_SECRET);
req.user = decoded;  // { userId, role, iat, exp }

// "Logout" — client deletes the token
// (server can't truly revoke unless using Redis blocklist)

The Access Token + Refresh Token Pattern

This solves JWT's biggest problem: you can't revoke tokens. The solution is two tokens.

// ACCESS TOKEN — short-lived (15 minutes)
// Sent in Authorization header on every API call
// If stolen, expires in 15 minutes → limited damage

// REFRESH TOKEN — long-lived (7 days)
// Sent in httpOnly cookie — JS can't read it
// Only used to get a new access token
// Stored in Redis → can be revoked instantly

// Flow:
// 1. Login → receive accessToken + refreshToken cookie
// 2. Call API with accessToken in header
// 3. accessToken expires → client calls POST /auth/refresh
// 4. Server validates refreshToken from cookie, issues new accessToken
// 5. Logout → server deletes refreshToken from Redis

// controllers/auth.controller.js
const loginHandler = async (req, res, next) => {
  try {
    const { user, accessToken, refreshToken } = await authService.login(req.body);

    // Set refresh token as httpOnly cookie
    res.cookie("refreshToken", refreshToken, {
      httpOnly: true,
      secure: process.env.NODE_ENV === "production",
      sameSite: "strict",
      maxAge: 7 * 24 * 60 * 60 * 1000
    });

    // Send access token in response body
    res.json({ success: true, data: { user, accessToken } });
  } catch (err) { next(err); }
};

Same Feature, Both Ways — "Log Out" and "Log Out Everywhere"

With sessions

// log out this device
app.post("/logout", (req, res, next) => {
  req.session.destroy((err) => {
    if (err) return next(err);
    res.clearCookie("sid").sendStatus(204);
  });
});
// log out everywhere: delete every
// session of the user from Redis

Takes effect instantly — the next request finds no session.

With JWT access + refresh tokens

// log out this device
app.post("/logout", async (req, res) => {
  const { jti } = jwt.verify(req.cookies.refreshToken, REFRESH_SECRET);
  await redis.unlink(`refresh:${jti}`);
  res.clearCookie("refreshToken").sendStatus(204);
});
// log out everywhere: logoutAll(userId)
// (see the Redis section, recipe 3)

The access token still works until it expires (e.g. 15 minutes) — that's why access tokens are kept short.

25API Versioning — How and Why

Keep old clients working while shipping new changes
Versioning
🧒 In simple words

Once apps are using your API, you can't change a response shape overnight — old app versions on people's phones would break. Versioning lets old and new clients use different versions side by side.

Real-life analogy: A bus route. You don't suddenly send bus 42 down a different road and strand everyone waiting at the old stops. You launch route 42A, keep 42 running for a while, announce the date it stops, and then retire it.

Remember: Adding fields is safe. Renaming, removing or changing the type or meaning of a field is a breaking change — ship it as /api/v2, keep v1 running, and announce when it will be retired.

Why Version Your API?

When you change an API (rename a field, remove a field, change a response structure), existing clients break. Versioning lets you ship v2 while keeping v1 running for clients that haven't updated yet — mobile apps especially, since users don't always update.

Graceful Shutdown — Don't Cut Requests in Half

When you deploy a new version, Docker (or Kubernetes) sends SIGTERM to the old container, waits (10 s by default for docker stop), then kills it with SIGKILL. Use that window to finish in-flight requests — imagine a money transfer halfway through.

src/server.js
const app = require("./app");
const pool = require("./db/pool");
const redis = require("./lib/redis");

const PORT = process.env.PORT ?? 3000;
const server = app.listen(PORT, () => console.log(`API listening on ${PORT}`));

let shuttingDown = false;
async function shutdown(signal) {
  if (shuttingDown) return;
  shuttingDown = true;
  console.log(`${signal} received — finishing in-flight requests…`);

  // 1. stop accepting new connections; callback runs when current requests finish
  server.close(async () => {
    // 2. close DB and Redis connections cleanly
    await Promise.allSettled([pool.end(), redis.quit()]);
    console.log("Clean shutdown complete");
    process.exit(0);
  });

  // 3. safety net: if something hangs, exit before Docker's SIGKILL
  setTimeout(() => process.exit(1), 9000).unref();
}

process.on("SIGTERM", () => shutdown("SIGTERM"));   // docker stop / Kubernetes
process.on("SIGINT", () => shutdown("SIGINT"));     // Ctrl+C in your terminal

A health endpoint that returns 503 while shuttingDown is true tells the load balancer to stop sending new traffic even sooner.

28Debugging — The Full Process

How to systematically find and fix bugs — not just guess and console.log
Debugging
🧒 In simple words

Debugging is finding out why the program does what it does, step by step, instead of changing code at random until the problem disappears.

Real-life analogy: A good doctor. They listen to the symptoms, form a guess, run a test to confirm it, and only then prescribe medicine. Random medicine might hide the symptom and leave the illness.

Remember: Read the whole error message (first line + first stack line in your code). Reproduce it, isolate it, fix the cause, then add a test or a log so it can't hide again.

The Debugging Mindset — 5-Step Scientific Process

Debugging is not random. It is a systematic elimination process. The developers who debug fast follow a process, not instinct.

  1. Reproduce the bug reliably
    Can you make it happen consistently? If yes — you can test your fix. If it's intermittent, log more before doing anything else. A bug you can't reproduce reliably is a bug you can't confirm you fixed.

  2. Isolate — find the smallest failing case
    Strip away everything that isn't needed to trigger the bug. Remove middleware, hard-code inputs, isolate the one function. The smaller the failing case, the easier to see the cause.

  3. Form a hypothesis
    Based on the error message and stack trace: "I think the problem is X because Y." State it explicitly. Don't just poke randomly.

  4. Test the hypothesis
    Make one change. Run again. Did it fix it? If yes — understand WHY before moving on. If no — discard the hypothesis, form a new one. One change at a time.

  5. Fix + verify + prevent
    Apply the real fix. Run the full test suite. Add a test that would have caught this bug — so it never silently reappears.

29Common Mistakes — Real Examples & Fixes

The mistakes every Node.js developer makes — and how to never make them again
Must Read
🧒 In simple words

Most backend bugs are not new. They are the same dozen mistakes that every developer makes, over and over. Learn them once and you'll spot them in code reviews instantly.

Real-life analogy: The "accident-prone zone" signs on a highway. They're placed where many drivers crashed before you. Reading the sign costs one second; ignoring it costs much more.

Remember: Each mistake below has a ❌ version and a ✅ fix. Many link back to the section that explains why.

❌ Mistake 1: await inside forEach

// forEach ignores async — nothing is actually awaited
users.forEach(async (user) => { await sendEmail(user.email); });
console.log("Emails sent"); // prints BEFORE any email is sent

✅ Fix: for...of or Promise.all

for (const user of users) { await sendEmail(user.email); } // sequential
await Promise.all(users.map(u => sendEmail(u.email)));     // parallel

❌ Mistake 2: No error handling in async routes

// If getUser() throws, Express gets an unhandled rejection → crash
app.get("/user/:id", async (req, res) => {
  const user = await getUser(req.params.id);
  res.json(user);
});

✅ Fix: try/catch + next(err) or upgrade to Express 5

// Express 4: explicit try/catch
app.get("/user/:id", async (req, res, next) => {
  try { res.json(await getUser(req.params.id)); }
  catch(err) { next(err); }
});
// Express 5: async errors auto-forwarded to errorHandler

❌ Mistake 3: Returning password in response

// Exposes password hash to the client!
const user = await prisma.user.findUnique({ where: { id } });
res.json(user);  // { id, name, email, password: "$2b$12$..." }

✅ Fix: select only safe fields

const user = await prisma.user.findUnique({
  where: { id },
  select: { id: true, name: true, email: true, role: true }
}); // password field never fetched

❌ Mistake 4: SQL Injection via string concatenation

// Input: email = "' OR '1'='1" → dumps all rows
const users = await db.query(`SELECT * FROM users WHERE email='${req.body.email}'`);

✅ Fix: parameterized queries ALWAYS

// mysql2 — ? placeholder
const [rows] = await pool.execute("SELECT * FROM users WHERE email = ?", [email]);
// Prisma — always parameterized internally
await prisma.user.findUnique({ where: { email } });

❌ Mistake 5: Not calling next() in middleware

// Request hangs forever — client gets a timeout
app.use((req, res, next) => {
  if (!req.headers.authorization) {
    console.log("missing auth");  // logs it, but no response, no next()
  }
  next();  // only reached if auth header exists!
});

✅ Fix: every code path must end

app.use((req, res, next) => {
  if (!req.headers.authorization)
    return res.status(401).json({ message: "Unauthorized" });  // END
  next();  // PASS ON
});

❌ Mistake 6: Forgetting to release DB connection in transaction

const conn = await pool.getConnection();
await conn.beginTransaction();
await conn.execute("...");
await conn.commit();
// ❌ No conn.release() — connection pool exhausts under load

✅ Fix: always release in finally

const conn = await pool.getConnection();
try {
  await conn.beginTransaction();
  await conn.execute("...");
  await conn.commit();
} catch(e) { await conn.rollback(); throw e; }
finally { conn.release(); }  // ✅ ALWAYS releases

❌ Mistake 7: Blocking the event loop with sync operations

// readFileSync blocks ALL requests while file loads
app.get("/export", (req, res) => {
  const data = fs.readFileSync("huge-report.csv");
  res.send(data);
});

✅ Fix: use async file operations

app.get("/export", async (req, res) => {
  const data = await fs.promises.readFile("huge-report.csv");
  res.send(data);
});  // or stream it for very large files

❌ Mistake 8: Updating cache but not the DB first

// If DB update fails, cache has stale/wrong data
await redis.set(`user:${id}`, JSON.stringify(newData));
await prisma.user.update({ where: { id }, data: newData });

✅ Fix: DB first, then invalidate cache

await prisma.user.update({ where: { id }, data: newData }); // DB first
await redis.del(`user:${id}`); // then DELETE cache (let it re-populate)

❌ Mistake 9: Sending two responses ("Cannot set headers after they are sent")

app.get("/users/:id", async (req, res) => {
  const user = await findUser(req.params.id);
  if (!user) res.status(404).json({ message: "Not found" });   // no return…
  res.json(user);                                               // …so this runs too → ERR_HTTP_HEADERS_SENT
});

✅ Fix: return when you respond early (see the HTTP section)

if (!user) return res.status(404).json({ success: false, message: "User not found" });
res.json({ success: true, data: user });

❌ Mistake 10: Forgetting the body parser

const app = express();
app.post("/users", (req, res) => {
  const { email } = req.body;   // TypeError: Cannot destructure property 'email' of 'req.body' as it is undefined (Express 5)
});

✅ Fix: app.use(express.json()) before the routes (see the JSON section)

app.use(express.json({ limit: "100kb" }));

❌ Mistake 11: CORS wildcard together with cookies

app.use(cors({ origin: "*", credentials: true }));   // browsers reject this combination

✅ Fix: an explicit list of allowed origins (see the CORS section)

app.use(cors({ origin: ["https://app.shopnow.in"], credentials: true }));

❌ Mistake 12: Awaiting before Promise.all (runs one after another)

const [user, orders] = await Promise.all([
  await getUser(id),       // waits 100 ms…
  await getOrders(id),     // …then waits 150 ms → 250 ms total, nothing in parallel
]);

✅ Fix: pass the promises, await only Promise.all (see the Async section)

const [user, orders] = await Promise.all([getUser(id), getOrders(id)]);   // ~150 ms

❌ Mistake 13: Keeping shared state in memory when running several processes

const loginAttempts = new Map();   // each cluster worker / container has its OWN map
// attacker's requests are spread over 4 processes → gets 4× the attempts

✅ Fix: shared state goes in Redis or the database (see Multithreading & Clustering)

const [[, attempts]] = await redis.multi().incr(key).expire(key, 900, "NX").exec();

❌ Mistake 14: A Redis lock with no TTL, released with plain DEL

await redis.set("lock:report", "1", "NX");   // crash → locked forever
await buildReport();
await redis.del("lock:report");              // may delete another server's lock

✅ Fix: SET key token NX PX + release only your own token (see the Locks section)

await withLock("lock:report", buildReport, { ttlMs: 60_000 });

❌ Mistake 15: Storing money as floating-point numbers

async function placeOrder(userId, items) {
  return prisma.$transaction(async (tx) => {
    let total = 0;

    // 1. Validate stock for each item
    for (const item of items) {
      const product = await tx.product.findUnique({ where: { id: item.productId } });
      if (!product)            throw AppError.notFound(`Product ${item.productId}`);
      if (product.stock < item.qty) throw AppError.badRequest(`${product.name} out of stock`);
      total += Number(product.price) * item.qty;
    }

    // 2. Create order + items in one shot
    const order = await tx.order.create({
      data: {
        userId,
        total,
        items: { create: items.map(i => ({ productId: i.productId, quantity: i.qty, unitPrice: i.price })) }
      },
      include: { items: { include: { product: { select: { name: true } } } } }
    });

    // 3. Deduct stock for all products in parallel
    await Promise.all(
      items.map(item =>
        tx.product.update({
          where: { id: item.productId },
          data:  { stock: { decrement: item.qty } }
        })
      )
    );

    // 4. Invalidate product caches
    await Promise.all(items.map(i => redis.del(`product:${i.productId}`)));

    // 5. Queue confirmation email (outside transaction — no rollback on email)
    await emailQueue.add("order-confirm", { orderId: order.id, userId });

    return order;
  });
  // If ANY step throws: DB rolls back, stock restored, no orphaned order
}

  const where = { isActive: true };
  if (search)   where.name = { contains: search, mode: "insensitive" };
  if (category) where.categoryId = Number(category);
  if (minPrice || maxPrice) where.price = {
    ...(minPrice && { gte: Number(minPrice) }),
    ...(maxPrice && { lte: Number(maxPrice) }),
  };

  // 3. Run count and data queries IN PARALLEL
  const skip = (Number(page) - 1) * Number(limit);
  const [total, products] = await Promise.all([
    prisma.product.count({ where }),
    prisma.product.findMany({
      where,
      orderBy: { [sort]: order },
      take: Number(limit),
      skip,
      include: { category: { select: { name: true } } },
    }),
  ]);

  const result = {
    data: products,
    pagination: { page:+page, limit:+limit, total, pages:Math.ceil(total/+limit), hasNext:skip+products.length<total }
  };

  // 4. Cache for 3 minutes
  await redis.set(cacheKey, JSON.stringify(result), "EX", 180);

31Capstone — Designing a Banking System (Money Transfers)

Everything in this guide working together: Express, JSON, headers, validation, MySQL transactions, row locks, idempotency, Redis, queues, clustering and Docker
Capstone
🧒 In simple words

We'll build the backend of a small bank wallet: users hold accounts, send money to each other, and see a statement. The hard part isn't the code — it's making sure that money is never created, lost or moved twice, even when thousands of requests arrive at the same moment, a user double-clicks, the network drops, or a server crashes half-way.

Real-life analogy: an old bank branch had a ledger book written in ink. Clerks never erased a line — mistakes were fixed by writing a new correcting line. Every transfer was written twice: once as money leaving one account, once as money arriving in another. At closing time they added everything up and the totals had to match. We'll copy exactly that, just in MySQL.

Remember: MySQL (transactions + row locks + constraints) protects the money. Redis only makes things faster and smoother. Idempotency keys make retries safe.

Step 1 — Requirements

Functional (what it does)

  • Users have one or more accounts (INR)
  • Transfer money between accounts
  • Deposits (e.g. from UPI / cash) and withdrawals
  • Account statement with running balance
  • Notifications after each transfer

Non-functional (how well it does it)

  • Correctness above everything — no negative balances, no double transfers
  • Safe retries — a timeout must never cause a second debit
  • Full audit trail — every rupee is traceable
  • Handles concurrent requests on the same account
  • Horizontally scalable API (many containers)

Step 2 — Six Design Principles (Learn These Even If You Never Build a Bank)

  1. Store money as whole numbers of the smallest unit (paise), never floats

    In JavaScript 0.1 + 0.2 is 0.30000000000000004. ₹12.50 is stored as 1250 in a BIGINT column. Convert to rupees only when displaying.

  2. Double-entry ledger

    Every movement creates two ledger rows: a DEBIT (money leaves an account) and a CREDIT (money arrives) of the same amount — just like the lines on your bank statement. For each transaction, total debits = total credits.

  3. The ledger is append-only

    Never UPDATE or DELETE a ledger row. A mistake is fixed by a new reversal transaction. That gives a perfect audit trail.

  4. Every money-moving request carries an idempotency key

    The client sends Idempotency-Key: <uuid>. If the same key arrives again (retry, double-click), the server returns the first result instead of moving money again.

  5. One DB transaction + row locks per transfer, always locked in the same order

    Lock both accounts with SELECT … FOR UPDATE in ascending id order, so two opposite transfers (A→B and B→A) can't deadlock.

  6. Redis never decides about money

    Redis is used for rate limits, OTPs, cached balances for display, job queues and "run once" locks for scheduled jobs.

Step 5 — The Transfer, Step by Step (Before Any Code)

  1. Validate the request

    Logged in? Body valid (zod)? Amount a positive integer? Idempotency-Key present? Different accounts?

  2. Start a DB transaction and lock both accounts in id order

    SELECT … WHERE id IN (?, ?) ORDER BY id FOR UPDATE. Any other transfer touching these accounts now waits.

  3. Check existence and ownership

    404 if an account doesn't exist, 403 if the "from" account isn't yours.

  4. Claim the idempotency key

    Insert the transactions row as PENDING. If the key already exists → roll back and return the original result (a replay).

  5. Business checks

    Both accounts ACTIVE? Same currency? Enough balance?

  6. Move the money

    Update both balances, insert the DEBIT and CREDIT ledger rows, mark the transaction COMPLETED.

  7. COMMIT

    All of it becomes visible at once. Any error before this → ROLLBACK → nothing happened.

  8. After commit

    Clear cached balances in Redis and queue the notification. These are "nice to have" — if they fail, the money is still correct.

src/services/transfer.service.js
const crypto = require("crypto");
const pool = require("../db/pool");                 // mysql2/promise pool
const AppError = require("../utils/AppError");

const fail = (status, code, message) => new AppError(message, status, { code });
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

function hashRequest({ fromAccountId, toAccountId, amount, currency, note }) {
  return crypto.createHash("sha256")
    .update(JSON.stringify([fromAccountId, toAccountId, amount, currency, note ?? ""]))
    .digest("hex");
}

// Public function: validation + retry on deadlock / lock timeout
async function transfer(input) {
  const { fromAccountId, toAccountId, amount } = input;
  if (!Number.isSafeInteger(amount) || amount <= 0)
    throw fail(400, "INVALID_AMOUNT", "Amount must be a positive whole number of paise");
  if (fromAccountId === toAccountId)
    throw fail(400, "SAME_ACCOUNT", "Cannot transfer to the same account");

  const requestHash = hashRequest(input);

  for (let attempt = 1; ; attempt++) {
    try {
      return await runTransfer(input, requestHash);
    } catch (err) {
      const retryable = err.code === "ER_LOCK_DEADLOCK" || err.code === "ER_LOCK_WAIT_TIMEOUT";
      if (!retryable || attempt === 3) throw err;
      await sleep(attempt * 50 + Math.random() * 50);   // back off, then rerun the WHOLE transaction
    }
  }
}

async function runTransfer({ userId, idempotencyKey, fromAccountId, toAccountId, amount, currency, note }, requestHash) {
  const conn = await pool.getConnection();          // every query below uses THIS connection
  try {
    await conn.beginTransaction();

    // ── 1. Lock both accounts, always in ascending id order (prevents deadlocks)
    const [rows] = await conn.query(
      `SELECT id, user_id, type, currency, balance, status
         FROM accounts WHERE id IN (?, ?) ORDER BY id FOR UPDATE`,
      [fromAccountId, toAccountId]
    );
    const from = rows.find((a) => a.id === fromAccountId);
    const to = rows.find((a) => a.id === toAccountId);
    if (!from || !to) throw fail(404, "ACCOUNT_NOT_FOUND", "Account not found");
    if (from.user_id !== userId) throw fail(403, "NOT_OWNER", "You can only send from your own account");

    // ── 2. Claim the idempotency key (UNIQUE index does the real work)
    let txId;
    try {
      const [ins] = await conn.query(
        `INSERT INTO transactions
           (initiated_by, idempotency_key, request_hash, type, status,
            from_account_id, to_account_id, amount, currency, note)
         VALUES (?, ?, ?, 'TRANSFER', 'PENDING', ?, ?, ?, ?, ?)`,
        [userId, idempotencyKey, requestHash, fromAccountId, toAccountId, amount, currency, note ?? null]
      );
      txId = ins.insertId;
    } catch (err) {
      if (err.code !== "ER_DUP_ENTRY") throw err;
      await conn.rollback();                          // release our locks first
      return await replayExisting(conn, userId, idempotencyKey, requestHash); // await: conn is released in finally
    }

    // ── 3. Business rules (checked on LOCKED, fresh rows — never on cache)
    if (from.status !== "ACTIVE" || to.status !== "ACTIVE")
      throw fail(422, "ACCOUNT_INACTIVE", "One of the accounts is frozen or closed");
    if (from.currency !== currency || to.currency !== currency)
      throw fail(422, "CURRENCY_MISMATCH", "Currency mismatch");
    if (from.balance < amount)
      throw fail(422, "INSUFFICIENT_FUNDS", "Insufficient balance");

    // ── 4. Move the money: balances + two ledger rows + status, all in this transaction
    const fromAfter = from.balance - amount;
    const toAfter = to.balance + amount;
    await conn.query("UPDATE accounts SET balance = ? WHERE id = ?", [fromAfter, from.id]);
    await conn.query("UPDATE accounts SET balance = ? WHERE id = ?", [toAfter, to.id]);
    await conn.query(
      `INSERT INTO ledger_entries (transaction_id, account_id, direction, amount, balance_after)
       VALUES (?, ?, 'DEBIT', ?, ?), (?, ?, 'CREDIT', ?, ?)`,
      [txId, from.id, amount, fromAfter, txId, to.id, amount, toAfter]
    );
    await conn.query(
      "UPDATE transactions SET status = 'COMPLETED', completed_at = NOW(3) WHERE id = ?",
      [txId]
    );

    await conn.commit();                              // ← the only moment anything becomes real
    return { id: txId, status: "COMPLETED", fromAccountId, toAccountId, amount, currency, replayed: false };
  } catch (err) {
    await conn.rollback().catch(() => {});           // undo everything (safe to call twice)
    throw err;
  } finally {
    conn.release();                                   // ALWAYS give the connection back to the pool
  }
}

async function replayExisting(conn, userId, idempotencyKey, requestHash) {
  const [[tx]] = await conn.query(
    `SELECT id, status, request_hash, from_account_id, to_account_id, amount, currency
       FROM transactions WHERE initiated_by = ? AND idempotency_key = ?`,
    [userId, idempotencyKey]
  );
  if (tx.request_hash !== requestHash)
    throw fail(422, "IDEMPOTENCY_KEY_REUSED", "This Idempotency-Key was already used for a different request");
  return {
    id: tx.id, status: tx.status, fromAccountId: tx.from_account_id, toAccountId: tx.to_account_id,
    amount: tx.amount, currency: tx.currency, replayed: true,
  };
}

🔍
Why the idempotency key needs no Redis lock: if two requests with the same key run at the same moment, they first queue up on the account row locks. When the second one finally inserts, the first has committed, so MySQL returns ER_DUP_ENTRY (1062) and we replay. Even without the row locks, InnoDB makes a second INSERT with the same unique value wait for the first transaction and then fail. The database already serialises duplicates for us.
⚠️
Failures are rolled back, not stored. If a transfer fails with "Insufficient balance", the transaction row disappears with the rollback, so the client may add money and retry with the same key. Some payment APIs store failures too; either is fine as long as it's documented. Also note mysql2 returns BIGINT as a JS Number by default — exact up to 253 paise (about ₹90 lakh crore), which is plenty for balances.

Money moved once; both clicks got the same answer.

Scenario C — Asha → Ravi and Ravi → Asha at the same time

T1 needs accounts (101, 205), T2 needs (205, 101). Because both lock ORDER BY id, both try 101 first. One waits for the other — no circular wait, no deadlock. If some other code path ever does cause a deadlock, MySQL kills one transaction with ER_LOCK_DEADLOCK and our retry loop runs it again.

Scenario D — The server crashes between the two balance updates

The transaction was never committed, so InnoDB rolls it back during recovery. Asha still has her money; Ravi never saw a credit. That's atomicity doing its job.

Step 12 — Reconciliation: Proving the Books Balance Every Night

-- 1. Every transaction is balanced: its debits equal its credits
SELECT transaction_id,
       SUM(CASE WHEN direction = 'DEBIT'  THEN amount ELSE 0 END) AS debits,
       SUM(CASE WHEN direction = 'CREDIT' THEN amount ELSE 0 END) AS credits
  FROM ledger_entries
 GROUP BY transaction_id
HAVING debits <> credits;                 -- expected: 0 rows

-- 2. Every stored balance equals the sum of its ledger
SELECT a.id, a.balance,
       COALESCE(SUM(CASE WHEN le.direction = 'CREDIT' THEN le.amount ELSE -le.amount END), 0) AS ledger_balance
  FROM accounts a
  LEFT JOIN ledger_entries le ON le.account_id = a.id
 GROUP BY a.id, a.balance
HAVING a.balance <> ledger_balance;       -- expected: 0 rows

-- 3. Money is never created or destroyed
SELECT SUM(balance) AS total FROM accounts;   -- expected: 0

Banking Design Checklist

  • Money in integer paise (BIGINT), never floats
  • Double-entry, append-only ledger; reversals instead of edits
  • CHECK constraints as the last line of defence
  • Idempotency key + UNIQUE index on every money-moving endpoint
  • One DB transaction per transfer; one dedicated connection
  • Lock rows in a fixed order; retry on deadlock
  • Decisions on locked primary rows — never cache or replica
  • Side effects (cache, queue) only after commit; outbox if critical
  • Rate limits + OTP for risky operations
  • Nightly reconciliation with alerts
  • Stateless API so it scales horizontally
  • Graceful shutdown so containers finish in-flight requests
